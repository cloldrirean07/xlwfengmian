# 平台案例完整度检查 v0.1

## 文档目的

这份文档说明当前新增的 `platform-case completeness` 是做什么的。

它解决的问题是：

- Obsidian 里的平台案例笔记已经建好了
- 但内容还是空壳，或者只填了零散观察
- 这时候如果直接同步到 `real-case`，只会把空信息继续传下去

所以它的定位是：

- 先检查上游平台案例笔记是否已经达到“值得同步”的最低完整度

## 当前代码落点

- 平台案例解析：`apps/web/src/domain/cases/parsePlatformCaseNote.js`
- 完整度检查：`apps/web/src/domain/cases/inspectPlatformCaseCompleteness.js`
- Markdown 报告：`apps/web/src/domain/cases/buildPlatformCaseCompletenessMarkdown.js`
- Obsidian 草稿包装：`apps/web/src/domain/cases/buildObsidianPlatformCaseCompletenessRecord.js`
- 报告脚本：`apps/web/scripts/report-platform-case-completeness.js`
- Obsidian 导出：`apps/web/scripts/export-obsidian-platform-completeness.js`

## 它检查什么

当前第一版先检查 12 个最影响后续判断质量的字段：

- 案例编号
- 来源平台
- 内容主题
- 内容目标
- 来源链接或素材路径
- 主体描述
- 视觉焦点
- 主点击机制
- 主封面方向
- 正向反馈词
- 可能调整方向
- 一句话结论

当前判断逻辑保持简单：

- 字段为空，视为未完成
- 字段仍是模板留白，视为未完成

## 当前状态分层

每条平台案例当前会被归到 3 类状态之一：

- `待回填`
  大部分关键字段还没填，暂时不适合同步
- `部分回填`
  已经有一些有效观察，但还没形成稳定判断
- `可进入同步`
  关键观察已基本具备，适合继续推进到 `real-case`

## 为什么这层要放在同步前

因为前面已经有：

- `sync:platform-note`
- `report:real-case-readiness`
- `generate:real-case-fill-sheet`

但如果最上游的平台案例笔记本身是空的，后面这些链路虽然能跑通，产出的还是低质量输入。

所以现在更合理的顺序是：

1. 先补平台案例笔记
2. 先跑 `platform-case completeness`
3. 确认达到最低完整度
4. 再同步到 `real-case`
5. 再继续 readiness / fill sheet / case run

## 当前阶段的意义

这层能力加上后，你后面补案例时会形成更清晰的主流程：

1. 建平台案例笔记
2. 跑完整度检查
3. 按缺失项补齐案例
4. 再执行同步
5. 再看真实案例 readiness

这样可以把“平台案例本身没写实”这类问题挡在最上游，而不是等同步后再发现。
