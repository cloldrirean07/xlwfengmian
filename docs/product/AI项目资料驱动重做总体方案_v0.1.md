# AI项目资料驱动重做总体方案 v0.1

## 1. 文档目的

本文档用于回答一个核心问题：

**如何参考当前 `AI封面创意助手` 已有内容，并按照 `/Users/xlw/Downloads/AI 项目资料` 中的方法论，重新组织、重做这个项目。**

这里的“重做”不等于删除现有成果。

更准确的目标是：

1. 保留已经沉淀出的规则、案例、输出链路和验证资产。
2. 用 AI 项目资料中的产研流程重新梳理项目。
3. 把当前偏“持续堆功能”的工程，重组为一条清晰的产品生产线。
4. 先完成方案确认，再进入 Requirement Spec、PRD、原型与代码实现。

## 3. AI 项目资料可复用的工作流

本次建议采用资料包中的五段式方法：

```text
全局 Rules
  -> 产品实现方案确认
  -> Requirement Spec / PRD
  -> 原型或前端实现
  -> 测试、审计、复盘与 updatelog
```

映射到当前项目：

1. `全局 Rules`
   - 作为本项目后续开发纪律。
   - 重点遵守：验证优先、方案先行、不跑不算、UI 文案产品化、变更留痕。

2. `ai-requirement-spec`
   - 用于每个功能先生成产品实现方案确认页。
   - 确认后再进入规格或实现。

3. `ai-prd-writer`
   - 用于沉淀正式 PRD。
   - 不再把需求散落在零碎讨论中。

4. `ai-pi-engine`
   - 用于从 Requirement Spec 进入维护模式实现。
   - 必须保护现有规则层、案例层和导出链路。

5. `code-review`
   - 用于阶段性审查安全、复杂度、错误处理和测试覆盖。

## 4. 三种重做方案

### 方案 A：保守重整

做法：

1. 保留当前 `apps/web` 技术栈和代码结构。
2. 只重做项目文档体系、需求确认流程和功能推进方式。
3. 每个后续功能都走“确认页 -> Requirement Spec -> 实现 -> 测试 -> 操作记录”。

优点：

1. 风险最低。
2. 不影响现有功能。
3. 能最快把资料包方法应用起来。

代价：

1. UI 和技术栈不会明显升级。
2. 当前静态页面结构仍会继续存在。
3. 对“重新做”的感知不强。

适合场景：

只是想学习 AI 项目资料的方法论，而不是立刻重构产品。

### 方案 B：产品线重做

做法：

1. 保留当前 `apps/web` 的规则层、案例层、导出链路和测试资产。
2. 重新定义产品主路径：
   - 输入准备
   - 首轮方向判断
   - 工作区深化
   - 二轮修订
   - 真实案例复盘
3. 先补齐新的产品实现方案、Requirement Spec 和 PRD。
4. 再逐步重组前端信息架构和交互，而不是直接推翻代码。

优点：

1. 保留已有资产，不浪费前期工作。
2. 能真正把项目从“工具集合”重做成“产品链路”。
3. 改造风险可控，每一步都能测试。
4. 适合继续长期做成一个真实 AI 产品。

代价：

1. 需要先做一轮产品架构整理。
2. 短期内不会马上看到大面积新 UI。
3. 每个阶段都需要确认边界，节奏更克制。

适合场景：

希望把该项目认真做成可持续迭代的 AI 产品。

### 方案 C：新建 Web v2

做法：

1. 在明确迁移计划后，新建 `apps/web-v2`。
2. 使用 React + TypeScript + Vite 作为新前端。
3. 旧 `apps/web` 作为规则和案例能力参考。
4. 逐步迁移核心接口和规则能力。

优点：

1. UI 和工程体验可以重新设计。
2. 更贴近 AI 项目资料中的项目初始化规范。
3. 适合做高质量新产品界面。

代价：

1. 风险最高。
2. 容易形成双项目并行维护。
3. 需要处理旧能力迁移、接口适配和测试重建。
4. 当前 README 明确不建议无计划新建平行目录。

适合场景：

已经确认当前静态 UI 无法承载目标产品，并愿意接受一轮迁移成本。

## 5. 推荐方案

推荐采用：

**方案 B：产品线重做**

原因：

1. 当前项目已有大量有效资产，推倒重来会浪费。
2. 真正的问题不是规则层不存在，而是产品主路径还需要重新收束。
3. AI 项目资料的价值不在于换技术栈，而在于把需求、方案、实现、验证、复盘串成稳定链路。
4. 方案 B 能把现有项目升级为更像真实产品的结构，同时保留继续重构 UI 的空间。

## 6. 推荐重做后的产品主线

建议把 `AI封面创意助手` 重做为五段主路径：

```text
输入准备
  -> 首轮方向判断
  -> 工作区深化
  -> 二轮修订
  -> 案例复盘与规则沉淀
```

### 6.1 输入准备

目标：

让用户用最少信息完成一次有效输入。

核心输入：

1. 内容主题
2. 内容目标
3. 平台
4. 素材类型
5. 素材描述
6. 想要的封面感觉

### 6.2 首轮方向判断

目标：

输出 3 个可比较的封面方向。

核心输出：

1. 方向标签
2. 点击机制
3. 封面大字
4. 标题建议
5. 配图方向
6. 风险提醒
7. 系统为什么这样判断

### 6.3 工作区深化

目标：

把首轮方向变成可继续执行的具体任务。

核心工作区：

1. 优化现有素材
2. 补内容贴合图
3. 做创意概念图

### 6.4 二轮修订

目标：

接住用户的主观反馈，把“更高级一点”“更炸一点”“别太营销号”转成结构化修订。

核心能力：

1. 识别保留项
2. 识别修改项
3. 输出新版方向
4. 解释修改依据

### 6.5 案例复盘与规则沉淀

目标：

让每一次真实案例都能反哺规则。

核心能力：

1. 真实案例回填
2. 批次试跑
3. 人工复盘
4. 写回 Obsidian
5. 规则修订任务单

## 10. 当前结论

当前最优路径不是“推翻重写”，而是：

**以现有项目为资产底座，用 AI 项目资料重新建立产品推进秩序，再按阶段重做主路径体验。**

这既能保留已有工程价值，也能让项目从“功能堆叠”转向“可持续产研闭环”。
