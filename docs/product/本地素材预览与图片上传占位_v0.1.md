# 本地素材预览与图片上传占位 v0.1

## 文档目的

这份文档记录 `apps/web` 为什么先接入“本地图片上传占位 + 本地预览”，而不是立刻做完整的图片上传、存储或图像理解。

这一步不是为了把图片链路一次做完，而是为了让产品形态先更贴近真实使用方式：

- 用户往往先有一张截图、参考图或内容相关图片
- 但第一版系统还不一定需要立刻上传到服务端
- 产品可以先把“本地素材上下文”引入决策链路，再逐步接更重的图像能力

## 当前实现了什么

### 1. 首轮输入区支持本地图片选择

现在首轮输入里已经新增：

- `上传图片`
- `清除预览`
- `本地素材预览区`

支持用户先放入：

- 内容截图
- 参考封面
- 内容相关图片
- 临时找来的辅助图

### 2. 只做浏览器本地预览，不上传服务器

当前逻辑明确控制在浏览器端：

- 通过 `File` + `URL.createObjectURL()` 生成本地预览
- 不发送到 `/api/analyze`
- 不写入后端文件系统
- 不增加服务端存储负担

这保证了第一版可以先验证：

- 用户会不会上传参考图
- 本地预览是否能帮助他更自然地填写素材描述
- 首轮输入是否更像真实创作场景

### 3. 当前预览会展示基础素材元信息

当前预览区会展示：

- 文件名
- 文件体积
- 图片尺寸
- MIME 类型

这一步的意义不是炫信息，而是为后续能力打基础：

- 判断图片是否适合进一步分析
- 判断是否是竖图、横图、低清图
- 判断后续是否需要压缩、裁剪、重构图

### 4. 当前结构已经为后续图片能力留了扩展口

虽然现在只做本地预览，但结构上已经可以继续接：

- 图片上传到服务端
- 截图 OCR / 图像理解
- 自动识别主体和构图
- 候选图推荐
- 图像生成或改图

换句话说，这次不是做一个“死的预览控件”，而是在首轮输入层先安放图片能力的入口。

## 为什么第一步先这样做

### 1. 更贴近真实用户输入

你前面已经明确过：

- 用户经常不是先写得很清楚
- 很多时候是有一张自己的图
- 或者有一个大概的封面效果想法

所以真实路径更像是：

- 先给图
- 再补内容
- 再让系统判断更适合怎么做封面

### 2. 不把第一版复杂度拉太高

如果一开始就直接做：

- 服务端上传
- 图像存储
- OCR
- 图像理解

会把第一版验证目标打散。

当前更适合先验证：

- 用户是否愿意把图片带进流程
- 页面是否开始形成“素材上下文”

### 3. 为后续规则和模型联动做准备

当前 `/api/analyze` 还主要依赖：

- 内容主题
- 内容目标
- 素材类型
- 素材描述
- 想要的封面感觉

而图片预览接入后，下一步很自然就能扩成：

- `assetImageContext`
- `assetVisualSignals`
- `imageFitHints`

这可以逐步进入分析层，而不是一次性硬接。

## 当前没有做什么

为了保持边界清楚，这版明确还没有做：

- 真正上传图片到服务端
- 图片持久化存储
- 图片 OCR
- 图片内容识别
- 预览图片参与 `/api/analyze` 请求
- 多图上传
- 拖拽排序

这些都属于后续扩展项，不应该和当前“本地素材入口验证”混在同一轮里。

## 当前前端状态变化

前端状态层现在新增：

- `assetPreview`

它当前承载：

- `objectUrl`
- `fileName`
- `mimeType`
- `sizeLabel`
- `dimensionsLabel`

并且在以下节点会被处理：

- 选择新图片时，替换旧预览
- 清除预览时，释放旧对象 URL
- 样例加载时，重置预览状态
- 页面卸载前，释放对象 URL

这样可以避免本地预览对象不断堆积。

## 当前结论

这次能力升级的核心价值，不在于“终于能上传图片了”，而在于：

- 首轮输入更接近真实产品使用
- 图片能力正式有了前端入口
- 后续接图像理解、找图、生图时不需要重做输入结构

## 下一步最值得继续加什么

围绕这层能力，下一步最值得继续做的是：

1. 上传图片后自动给出 `素材类型建议`
2. 预览图旁边增加 `我想保留什么 / 我想替换什么`
3. 把图片上下文接入分析请求的占位字段
4. 增加图片对比视图，为二轮优化服务
