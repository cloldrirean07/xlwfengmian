# AI项目资料严格重做范围判断 v0.1

## 1. 判断结论

本次结论：

**不是仅仅做产品线重做，但也不建议推倒全部重写。**

更准确的改造方式是：

**以产品线重做为主轴，同时重做文档生产线、需求确认机制、首页信息架构和阶段交付纪律；保留已验证可用的规则、案例、导出和测试资产。**

## 3. 按 AI项目资料 应该重做什么

### 3.1 必须重做：文档生产线

当前问题：

1. 文档数量很多，但不完全符合资料包中的阶段化结构。
2. 方案确认、Requirement Spec、PRD、架构计划、操作记录之间还没有形成统一链路。
3. 后续需求容易继续变成“边讨论边堆功能”。

重做目标：

1. 每个重要需求先生成 HTML 产品实现方案确认页。
2. 用户确认后再生成 Requirement Spec 或 PRD。
3. 进入实现前必须明确实现边界。
4. 每次完成后写入 operations 记录。

建议新增或补齐：

1. `docs/.requirement-preview/AI封面创意助手重做_方案确认_latest.html`
2. `docs/prd/AI封面创意助手重做_Requirement_Spec_v0.1.md`
3. `docs/prd/AI封面创意助手_MVP重做_PRD_v0.1.md`
4. `docs/architecture/AI封面创意助手产品线重做架构计划_v0.1.md`

### 3.2 必须重做：产品主路径

当前问题：

1. 项目已经有很多能力，但用户主路径不够收束。
2. 首页同时展示输入、解释、真实案例、复盘看板等多个目标，信息密度偏高。
3. 工作区、二轮修订和案例复盘还没有被讲成一条自然路径。

重做目标：

把产品主路径收束为：

```text
输入准备
  -> 首轮方向判断
  -> 工作区深化
  -> 二轮修订
  -> 案例复盘与规则沉淀
```

### 3.3 必须重做：首页与工作台信息架构

当前问题：

1. 首屏解释内容偏多。
2. 页面更像项目验证台，不像给真实用户使用的产品工作台。
3. 部分文案仍偏项目说明和开发说明。

重做目标：

1. 首屏直接服务“输入并生成封面方向”。
2. 把验证说明降级到辅助区。
3. 用产品语言表达状态和操作，不面向开发者解释实现过程。
4. 保留已有静态前端方式，不先引入新框架。

### 3.4 必须重做：需求到实现的确认门

当前问题：

1. 之前项目已经沉淀很多局部功能，但不是每一段都先经过统一确认页。
2. 后续继续做大改造时，如果没有确认门，会很容易范围失控。

重做目标：

1. 先确认范围。
2. 再生成规格。
3. 再进入维护模式实现。
4. 实现后必须测试。

## 4. 应该保留什么

### 4.1 保留：规则引擎

保留原因：

1. 已经支撑 5 类封面方向。
2. 当前测试通过。
3. 是产品判断能力的核心。

后续只做局部整理，不推倒重写。

### 4.2 保留：案例体系

保留原因：

1. 真实案例、平台案例、批次复盘已经形成数据资产。
2. 这是产品区别于普通 Prompt 工具的关键。

后续重做时应把案例体系放回主路径，而不是删除。

### 4.3 保留：Obsidian 导出与安全写回链路

保留原因：

1. 该链路已经有大量测试覆盖。
2. 它连接项目执行层和知识库沉淀层。

后续可以整理入口，不重写底层能力。

### 4.4 保留：Node 测试体系

保留原因：

1. 当前 `npm test` 已通过 178 项。
2. 它是后续改造的安全基线。

后续每次实现后必须继续执行。

## 5. 暂不重做什么

### 5.1 暂不新建 `apps/web-v2`

原因：

1. 项目 README 已明确不建议无计划创建平行目录。
2. 当前代码基线可用。
3. 现在更需要主路径重做，而不是先换技术栈。

如果后续确认要 React + TypeScript + Vite，需要先单独生成迁移方案。

### 5.2 暂不接真实生图模型

原因：

1. 当前产品核心仍是方向判断与策略建议。
2. 过早接生图会扩大风险。
3. 规则和工作区链路应先稳定。

### 5.3 暂不重写 Obsidian 导出系统

原因：

1. 当前已有复杂测试覆盖。
2. 本轮目标是重做产品主路径，不是重做知识库同步底座。

## 6. 严格推荐方案

推荐方案：

**产品线重做 + 文档生产线重做 + 首页信息架构重做。**

不推荐：

1. 只做产品线重做。
2. 直接新建 Web v2。
3. 直接大改 UI。
4. 先接模型或生图能力。
