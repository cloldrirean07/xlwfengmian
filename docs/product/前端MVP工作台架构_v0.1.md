# 前端 MVP 工作台架构 v0.1

## 文档目的

这份文档记录 `apps/web/public/` 这一层为什么要从单文件脚本，拆成更适合继续扩展的前端工作台结构。

它服务的是一个很明确的目标：

- 现在先把 `第一轮方向判断 -> 第二轮改单 -> Prompt/LLM Draft -> 平台案例复核入口` 串成一个可演示的 MVP
- 之后继续接 `图片上传 / 候选图排序 / 找图 / 生图 / 用户反馈回流` 时，不需要把前端重写一遍

## 当前前端结构

- `public/index.html`
  页面骨架，负责表达工作台分区
- `public/styles.css`
  MVP 视觉层和响应式布局
- `public/main.js`
  前端入口，只负责启动应用
- `public/app/createApp.js`
  事件编排和页面流程控制
- `public/app/api.js`
  前端对后端 API 的调用封装
- `public/app/dom.js`
  DOM 引用集中管理
- `public/app/renderers.js`
  页面渲染、卡片渲染、状态渲染
- `public/app/state.js`
  当前会话状态

## 为什么要这样拆

### 1. 把“流程控制”和“页面输出”分开

如果后续继续把所有逻辑写在 `main.js`，很快就会出现几个问题：

- 页面越来越长
- 一处状态变化要改多个位置
- 接模型、接上传、接案例时很难定位边界

现在拆分之后：

- `createApp.js` 负责流程
- `renderers.js` 负责展示
- `api.js` 负责请求

这样未来接入真实能力时，改动面会更小。

### 2. 保留未来多端扩展的余地

你前面已经明确：

- 手机端重便利
- 电脑端重专业
- 第一版更适合先做网页 H5 / Web 工作台

这一版前端结构，是为了后面继续支持：

- `mobile-like input flow`
- `desktop review workspace`
- `internal operations panel`

而不是把 MVP 写成一次性 demo。

### 3. 让当前产品结构更接近真实 AI 产品

这次页面不只展示输入和输出，还明确分成了：

- `MVP Workbench`
  用户首轮输入
- `Decision Frame`
  系统如何判断
- `First Round`
  三张方向卡
- `Second Round`
  反馈改单
- `Model Layer`
  Prompt / LLM Draft
- `Operations Desk`
  Obsidian 案例复核台

这对应的是一个真实产品从：

- 用户使用层
- 规则判断层
- 模型生成层
- 运营复核层

逐层分开的结构。

## 当前页面重点验证什么

这一版前端不是为了证明“已经能出最终好封面”，而是为了验证：

### 1. 用户是否能完成最小输入

当前最小输入依然围绕：

- 内容主题
- 内容目标
- 素材类型
- 素材描述
- 想要的感觉

### 2. 三张卡片是否真的有差异

首轮结果现在会明确展示：

- 主点击机制
- 内容类型
- 输入模式
- 匹配信号
- 封面大字
- 标题建议
- 配图主策略
- 构图建议
- 候选配图方向
- 优先推荐顺序

### 3. 第二轮是否能保留主方向继续改单

当前二轮结构已经能验证：

- 用户保留什么
- 用户想改什么
- 系统识别出哪个主变量需要动
- 新方向是否仍然保持原卡的骨架

### 4. 页面是否为后续接图片能力留好了口

当前虽然还没接上传图片，但结构上已经给未来的能力留了接口：

- `素材类型`
- `素材描述`
- `候选配图方向`
- `候选图优先顺序`

后续如果增加：

- 上传截图
- 图像识别
- 找图推荐
- 图像生成

都可以沿着这个结构继续扩，而不是另起炉灶。

## 下一步最适合继续加什么

按当前产品阶段，前端下一步最值得加的是：

1. `上传图片占位能力`
   先支持本地图片预览和文件状态，不急着做真正上传存储
2. `选中卡片后的对比视图`
   让用户更容易理解一轮和二轮改了什么
3. `案例输入模板`
   让不同赛道用户更快起步
4. `平台案例复核结果跳转`
   从复核结果直接打开待补字段工作单

## 当前结论

这次前端改动的重点，不是把 UI 做得花，而是先把代码结构和产品结构对齐：

- 页面像真实产品工作台
- 前端代码边界清楚
- 后续接上传、接模型、接案例库时不需要推倒重来
