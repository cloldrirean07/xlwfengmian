# 规则引擎与输入结构 v0.1

## 文档目的

这份文档记录当前 `apps/web` 第一版正式产品内核的两项关键升级：

- 将 `5 类封面效果方向` 沉到代码规则层，而不是只停留在 Obsidian 描述
- 将输入结构从纯文字主题，推进到 `内容说明 + 素材描述 + 想要的封面感觉`

它的作用不是替代 PRD，而是帮助后续开发、调试和规则迭代时快速对齐：

- 现在代码到底如何判断主方向
- 现在第一轮卡片具体由哪些字段生成
- 下一步应该往哪里扩，而不是重复返工

## 当前代码落点

- 输入抽取：`apps/web/src/domain/analysis/extractInputFields.js`
- 方向排序：`apps/web/src/domain/analysis/rankDirectionCandidates.js`
- 效果规则库：`apps/web/src/domain/effects/coverEffectCatalog.js`

- 第二轮反馈改单：`apps/web/src/domain/refinement/`

## 当前输入结构

当前第一轮最小输入已经对齐到更真实的产品表述：

- `contentTopic`
  用户这条内容大概讲什么
- `contentGoal`
  用户希望点开后传达什么价值
- `userAssetType`
  当前素材类型
- `assetDescription`
  用户现有画面/截图/想法的自然语言描述
- `referencePreference`
  用户想要的封面感觉
- `assetNotes`
  额外补充说明

当前系统会额外生成：

- `minimumInputMode`
  区分是只有内容说明，还是已经带素材描述
- `contentTypePrimary`
  当前更像教程、观点、误区纠正、结果展示等哪类内容
- `clickDriverPrimary`
  当前更靠看懂、收益、好奇、冲击、信任中的哪种点击机制

## 当前 5 类封面效果方向在代码中的定位

当前效果方向不是 UI 标签，而是规则引擎的稳定骨架。

包含：

- `information`
  强信息感
- `result`
  强结果感
- `suspense`
  强悬念感
- `conflict`
  强冲突感
- `texture`
  强质感感

每个方向目前都在规则库里定义了：

- 用户可见标签
- 点击机制
- 适合内容
- 常见反馈关键词
- 风险边界
- 封面大字模板
- 标题模板
- 按素材类型拆分的配图策略
- 构图建议

## 当前第一轮卡片输出结构

当前每张方向卡片除了基础文案，已经开始携带规则解释字段：

- `effectId`
- `directionTypeInternal`
- `directionLabelUserFacing`
- `directionDescription`
- `coverCopyMain`
- `titleOptions`
- `imageDirection`
- `imageDirectionCandidates`
- `compositionDirection`
- `rankedImageStrategies`
- `clickReason`
- `riskNote`
- `bestFor`
- `signalMatches`

其中最关键的两个新字段是：

- `bestFor`
  告诉用户这类卡片更适合什么内容
- `signalMatches`
  告诉用户系统为什么给出这个方向

当前还新增了：

- `imageDirectionCandidates`
  把“该怎么找图/怎么补图”拆成多个候选方向，而不是只给一句笼统建议
- `rankedImageStrategies`
  在候选方向之上，再给出当前更建议先尝试的顺序和原因

这一步的意义，是把“像顾问一样解释判断”带进产品结果里。

## 当前判断逻辑

当前方向排序仍然保持第一版轻量实现，但已经明确围绕 3 类得分：

- `fitScoreContent`
  内容本身适不适合这个方向
- `fitScoreAsset`
  当前素材类型适不适合这个方向
- `fitScorePlatform`
  当前平台环境下，这个方向是否天然更容易成立

最终只输出前 3 个方向卡片：

- 1 个主方向
- 2 个备选方向

## 当前候选配图方向结构

当前第一轮卡片里的候选配图已经开始拆成可继续扩的结构：

- `优化现有素材`
  先围绕当前截图/画面做提炼
- `补内容贴合图`
  当原素材不够强时，补一张更贴内容的辅助图
- `做创意概念图`
  当用户只有内容想法，或想拉开和普通封面的差距时，先确定能承载点击机制的主体

每个候选方向当前都会带：

- `label`
- `assetSource`
- `description`
- `usageCondition`

这一步是在为未来的“找图 / 排序 / 生图”留接口，而不是现在就把它们一次做完。

## 当前候选图优先级排序

在候选配图方向的基础上，当前系统又补了一层轻量排序：

- `优化现有素材`
- `补内容贴合图`
- `做创意概念图`

系统会根据当前输入，给每个策略附带：

- `priorityScore`
- `priorityReason`

当前排序主要看三类信号：

- 用户是否已经有可用素材
- 当前素材是否普通、是否不够贴内容
- 当前封面方向更依赖哪种点击机制

这一步的价值不是做精确算法，而是让产品开始回答：

- 你应该先改现有图，还是先补图库图
- 这条内容值不值得直接走创意概念图
- 为什么系统推荐你先走这条路径

## 当前第二轮反馈映射升级

第二轮不再只做简单关键词匹配，当前已经开始区分：

- 用户想保留的强项
- 用户想修正的问题

当前代码会从反馈里同时识别：

- `feedbackPreservedSignal`
- `preservedVariable`
- `feedbackTargetVariable`
- `feedbackMatchedKeywords`

这意味着系统开始能理解：

- 哪一部分是用户认可的
- 哪一部分是用户希望修改的

例如：

- “高级，但太平”
  会更偏向保留 `质感`，补 `悬念/冲突`
- “很抓人，但别太像营销号”
  会更偏向保留 `悬念/冲突`，补 `质感`

## 当前真实案例契约升级

代码侧案例数据现在也正式纳入了：

- `assetDescription`

也就是说，真实案例和样例数据不再只存：

- 主题
- 目标
- 素材类型

还会明确记录：

- 用户现有的画面/截图是什么
- 用户缺的是什么图

这让后面的真实案例回填能更贴近产品实际输入。

## 第三阶段规则沉淀接入

产品线重做第三阶段不直接修改 5 类方向规则本体，而是先把真实案例复盘结果接成规则沉淀前置判断。

当前规则沉淀依据来自：

- 批次复盘看板中的人工复盘覆盖趋势
- 跨批次摩擦点汇总中的重复类别数
- UI 优化进入条件报告中的 readiness level
- 人工复盘待补任务中的缺失字段

当前代码侧展示已增加：

- `规则沉淀判断`
- `Web v2 判断`
- `视觉重构判断`

当前判断原则：

1. 如果人工复盘仍缺关键字段，先补人工复盘，不进入 Web v2 或完整视觉重构。
2. 如果 UI readiness、人工复盘覆盖和重复摩擦点同时达标，先进入主链路局部 UI 优化讨论。
3. 即便进入 UI 优化讨论，也优先围绕主链路局部优化，不直接新建 Web v2。
4. 只有当后续复盘持续证明“现有页面结构本身”成为稳定瓶颈时，再重新评估 Web v2。

## 这轮升级解决了什么

### 1. 规则不再只存在于文档
现在已经有一层真正可调用的规则库，后续可以继续往里补案例、反馈词和边界。

### 2. 输入更贴真实使用场景
用户不一定会上传最终素材，但通常能描述：

- 我现在有什么图
- 我想做成什么感觉

这比单纯让用户写一个主题，更接近真实产品路径。

### 3. 第一轮卡片开始具备“解释性”
系统不只是给结果，还开始解释：

- 为什么推荐这个方向
- 这个方向适合什么内容
- 对当前素材该怎么用图
- 当前更建议先走哪种配图路径

### 4. 第一条真实案例桥接已经起出
当前已创建：

- 代码侧：`real-001`
- Obsidian 占位映射：`P-01`

并且已经验证通过：

- `validate:cases`
- `run:case -- --case-id real-001`
- `export:obsidian-case -- --case-id real-001`
- `report:case-progress`

### 5. 真实案例就绪度可以被代码侧单独检查
现在不仅能看“这条案例有没有进代码层”，还能看：

- 它是不是还停留在模板态
- 还缺哪些字段
- 现在能不能进入人工验证

## 暂时还没做的部分

当前仍然没做这些能力：

- 真图片上传与识别
- 直接生成封面图
- 真候选图检索
- 多轮复杂视觉编辑
- 数据化点击率预测

这是刻意保留的边界，不是遗漏。

## 下一步建议

最适合继续推进的顺序：

1. 将 `用户反馈词库` 进一步映射到第二轮改单变量
2. 将 `rankedImageStrategies` 接到后续候选图检索或人工找图链路
3. 增加 `真实案例回填 -> 规则修订` 的闭环记录
4. 等真实案例积累到一定数量后，再决定是否上图像模型或检索模块
