# AI封面创意助手 Skills 驱动产品重梳理 v0.1

生成日期：2026-08-09

## 1. 本轮重梳理依据

本轮依据来自两类材料：

- 用户原始需求与后续追问整理：确认产品不是单纯的封面排版工具，而是面向内容创作者的“封面创意选图 + 点击方案生成器”。
- `AI 项目资料/2、产研优质Skills` 中的产研 Skills：确认后续不应直接继续堆功能，而应重新按“需求确认、Requirement Spec、PI Engine 实现、PRD 固化、设计优化”的顺序推进。

## 2. 当前项目核心判断

当前项目的正确方向应从“内部规则验证台”收束为“创作者体验 MVP”。

产品主链路应是：

```text
输入内容想法 / 上传已有素材
-> 理解内容主题、素材特点、目标平台
-> 匹配适合的封面图题材与点击心理
-> 输出 3 个创意封面方案
-> 用户选择一个方向或反馈修改
-> 二轮微调标题、选图方向、构图建议
-> 沉淀为真实案例和规则样例
```

这意味着：规则、复盘、写回、样例复跑仍然重要，但它们应作为后台支撑系统，不应成为创作者进入产品后的第一感受。

## 3. Skills 对项目的重新分工

### 3.1 requirement-spec-architect

用途：把模糊需求整理成“可确认、可实现、可交给工程原型实现”的 Requirement Spec。

在本项目中，它应该负责：

- 先生成“产品实现方案确认页”，让用户确认本轮到底做什么。
- 把“封面创意素材匹配模块”拆成输入、输出、页面、流程、状态、分支。
- 明确哪些是本轮范围，哪些不做。
- 产出给 PI Engine 使用的正式 Requirement Spec。

注意：Requirement Spec 不是 PRD，也不是技术方案，不写数据库、不写接口设计、不写长期商业规划。

### 3.2 ai-pi-engine

用途：根据 Requirement Spec 改造或实现前端原型。

在本项目中，它应该负责：

- 进入已有项目维护模式，而不是新开一个项目。
- 只实现 Requirement Spec 中确认过的功能。
- 保护当前已有能力：创作者首页、真实案例、标题候选、优选标题写回、案例记录。
- 把“创作者主链路”做顺，而不是继续暴露内部规则工作台。

PI Engine 的使用时机：必须在 Requirement Spec 确认之后。

### 3.3 ai-prd-writer

用途：在产品结构稳定后，生成正式 PRD。

在本项目中，它应该负责：

- 先输出 PRD 信息架构确认。
- 用户确认信息架构后，再写正式 PRD。
- 正式 PRD 用于对外沟通、团队协作、后续长期迭代。

注意：现阶段不建议先写大 PRD 再开发。这个项目还在真实案例验证阶段，更适合先用 Requirement Spec 驱动 MVP 跑通。

### 3.4 frontend-design

用途：把前端界面做成真实可用、视觉有辨识度的产品体验。

在本项目中，它应该负责：

- 把首页从内部工具感，调整为创作者能理解的产品入口。
- 强化“上传素材 -> 得到封面创意方案”的直觉。
- 减少规则、复盘、写回等内部术语对用户的干扰。
- 在真实案例链路跑顺后，再统一优化视觉层次、动效、卡片结构和空态。

注意：设计不应先于主链路。当前最重要的是先确认产品流程，再做美化。

### 3.5 计划、评审、冻结类 Skills

用途：作为每轮迭代的检查门。

在本项目中，它们应被用作：

- 需求开始前：确认本轮目标和范围。
- 实现前：冻结 Requirement Spec，避免边做边变。
- 实现后：检查是否偏离原需求。
- 案例复跑后：判断是产品问题、规则问题，还是样例信息不足。

## 4. 后续推荐执行顺序

推荐从现在开始按以下顺序推进：

```text
产品追问清单
-> 封面创意素材匹配模块：产品实现方案确认
-> Requirement Spec
-> PI Engine 维护模式实现
-> real-002 / real-003 / new-001 真实案例验证
-> 根据验证结果修规则、修输入、修页面
-> PRD 信息架构确认
-> 正式 PRD
```

## 5. 下一轮最适合做的模块

下一轮建议做：

```text
封面创意素材匹配模块 v0.1
```

它是这个项目从“标题/规则实验”转向“真正产品”的关键模块。

### 5.1 模块目标

让创作者上传已有素材或输入内容想法后，系统不只是评价现有图片，而是给出更适合内容传播的封面创意方向。

### 5.2 输入

- 内容主题
- 目标平台
- 已有图片、截图或素材说明
- 内容目标
- 用户偏好的标题或表达方向

### 5.3 输出

每轮输出 3 个封面创意方案，每个方案包含：

- 方案名称
- 推荐封面图题材
- 当前素材是否可直接使用
- 是否建议补图
- 标题方向
- 构图建议
- 点击理由
- 风险提醒

### 5.4 关键判断

系统需要判断：

- 当前素材是“可直接做封面”，还是“只能作为内容理解参考”。
- 当前内容更适合美食冲击、情绪氛围、结果展示、反差悬念，还是教程价值。
- 标题应该走情绪型、教程型、种草型、悬念型，还是反差型。

## 6. 现在不建议继续做什么

当前不建议继续优先做：

- 继续扩展后台复盘和写回功能。
- 继续采集大量标题，但没有先定义标题风格库结构。
- 直接接入真实模型输出，但没有先固定输入输出字段。
- 大规模重做 UI，但主链路还没有确认。
- 把上传图片能力只做成“选一张图”，因为用户真实需求往往是多素材、多截图、多内容参考。

这些事情不是不重要，而是顺序应放在主链路确认之后。

## 7. 推荐下一步

下一步应使用 `requirement-spec-architect` 的方式，先生成：

```text
封面创意素材匹配模块_产品实现方案确认_v0.1
```

确认页应包含：

- 需求等级
- 需求目标
- 本次范围
- 页面与功能拆解
- 产品实现流程
- 关键状态流转
- 关键分支说明
- 成文前需确认的问题

用户确认后，再生成正式 Requirement Spec，并交给 PI Engine 进入维护模式实现。

## 8. 本轮结论

本项目后续不应继续围绕“规则系统本身”展开，而应让规则系统退到后台，服务一个更清晰的创作者产品链路。

一句话方向：

```text
帮助创作者从内容素材中快速得到 3 个更有点击欲望的封面创意方案。
```
