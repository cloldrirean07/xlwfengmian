# 批次试跑人工结论填写前置_v0.1

## 1. 本次补的是什么

在“批次试跑记录预览”阶段，新增一层可执行的人工结论填写指引。

不是只给用户一整段 Markdown 草稿，而是提前告诉他：

- 先填哪 4 个关键判断
- 每个判断为什么重要
- 建议按什么顺序写
- 写的时候优先参考哪些当前批次信号

## 2. 为什么现在要补这层

前一阶段我们已经能：

- 生成批次试跑记录
- 读取 Obsidian 中人工填写的结论
- 汇总哪些批次还没写人工结论

但中间仍缺一步：

- 用户看到试跑记录后，不一定知道先补什么

这会导致：

- 人工结论填写成本高
- 各批次填写口径不稳定
- 后续跨批次汇总虽能读取人工结论，但信号不够整齐

所以这次补的是“填写前置引导”，不是 UI 美化。

## 3. 当前实现方式

新增领域层构造器：

- `apps/web/src/domain/cases/buildBatchRunManualReviewGuide.js`

它负责返回：

- `headline`
- `reason`
- `completionRule`
- `fillOrder`
- `supportingSignals`
- `suggestedWorkflow`

这意味着“人工结论怎么填”现在是代码侧结构化能力，不是前端硬编码文案。

## 4. 当前前置的 4 个关键判断

当前固定优先前置：

1. 最卡环节
2. 问题类型
3. 最该前置模块
4. UI 时机

原因很直接：

- 这 4 项最影响后续跨批次判断
- 也最影响“要不要开始 UI 优化”的产品决策

## 5. 接入位置

应用层：

- `apps/web/src/application/runRealCaseBatchRunRecordPreview.js`

领域层：

- `apps/web/src/domain/cases/buildBatchRunManualReviewGuide.js`
- `apps/web/src/domain/cases/buildRealCaseBatchRunRecordMarkdown.js`

前端渲染：

- `apps/web/public/app/renderers.js`

## 6. 当前前端会多显示什么

批次试跑记录预览区现在会新增：

- 先补这 4 个关键人工判断
- 填写顺序提示
- 填写时可先参考的信号

所以这块工作台现在更像“可继续执行的复盘面板”，而不是一份单纯导出预览。

## 7. 为什么这层比先优化 UI 更重要

如果连人工结论该怎么写都不够顺手，现在直接改 UI，仍然容易陷入：

- 界面变得更好看
- 但真实试跑记录质量没有提升
- 跨批次汇总证据还是不稳定

这次补强的价值在于：

- 先让试跑复盘更容易发生
- 再让 UI 判断建立在更真实的输入上

## 8. 当前判断

现在已经更接近可以讨论 UI，但仍不建议马上做大改版。

更稳的流程是：

1. 继续跑真实批次
2. 用前置指引补人工结论
3. 看关键判断是否开始跨批次重复
4. 再正式讨论 UI 优化

## 9. 下一步建议

下一步最有价值的是：

1. 用现有工作台生成一批试跑记录
2. 按前置指引补完整人工结论
3. 再生成跨批次摩擦点汇总
4. 看人工字段覆盖度和待补批次是否开始改善

如果改善明显，再进入 UI 优化专题会更有把握。
