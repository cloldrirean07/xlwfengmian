# 首页页面分层与拆页建议_v0.1

## 1. 文档目的

这份文档要解决的问题是：

当前 `apps/web/public/index.html` 已经不是一个只做首轮 demo 的页面，而是同时承载了：

- 用户主链路
- 产品验证链路
- 真实案例维护链
- 内部复盘与运维链

这些能力本身都成立，但继续全部堆在首页，会带来两个问题：

1. 首页越来越像“总控制台”，而不像一个真实产品入口
2. 后续做 UI 优化时，很难判断到底是在优化用户主流程，还是在优化内部运维页面

所以这一轮不是直接改页面，而是先把首页应该承担什么、不应该长期承担什么，整理成清晰结构。

## 2. 当前首页的 4 层内容

根据现有页面，首页内容可以明确拆成 4 层。

### 2.1 第一层：用户主链路

包括：

- Hero
- workflow strip
- 第一轮输入
- 系统当前怎么判断
- 第一轮方向结果
- 下一步工作区
- 第二轮优化
- 第二轮优化结果

这一层的职责是：

- 承载你真正要验证的产品体验
- 让用户完成一次从输入到二轮优化的完整路径

这是首页最应该保留的核心。

### 2.2 第二层：主链路辅助能力

包括：

- `Prompt 与 LLM Draft`
- `样例运行结果`

这一层的职责不是主产品流程本身，而是：

- 帮助你验证模型接口层是否顺
- 帮助你快速复跑固定样例

它们与主链路强相关，但主要服务内部验证，不一定适合长期暴露在首页主视图。

### 2.3 第三层：真实案例维护链

包括：

- `真实案例录入预览台`
- `真实案例骨架预览`
- `批量真实案例录入`
- `批量写入预览`
- `真实案例已写入概览`
- `平台案例复核台`

这一层的职责是：

- 把真实案例从文档沉淀推进到代码结构
- 支撑案例库持续增长、复核、回填和维护

这已经不只是“补一个表单”，而是一条独立维护链。

### 2.4 第四层：复盘与 UI 进入判断链

包括：

- `UI 优化进入条件报告`
- `跨批次摩擦点汇总`
- `批次复盘看板`

这一层的职责是：

- 判断是否值得系统讨论 UI
- 汇总多批次证据
- 决定下一轮应该先改规则、改结构还是改页面

它本质上是“产品推进驾驶舱”，不是面向普通使用者的前台能力。

## 3. 当前真正的问题不在功能，而在信息架构

从产品推进角度看，现在的问题不是：

- 功能做多了
- 模块不成立

而是：

- 首页把前台产品、后台维护、验证驾驶舱都混在了一起

这样会带来 3 个具体后果：

1. 主链路不够突出  
用户打开后，不容易立刻理解“最该从哪里开始用”。

2. 运维能力抢占了前台注意力  
录入、回填、导出、复盘、同步这些动作密集出现，会稀释首轮产品体验。

3. UI 优化目标容易失焦  
如果首页既是产品页又是运维页，那么任何 UI 讨论都会混杂两类目标。

## 4. 首页长期应该保留什么

当前建议首页长期保留以下 3 块。

### 4.1 产品总叙事层

保留：

- Hero
- workflow strip

价值：

- 说明产品当前验证边界
- 说明这版先做什么、不做什么

### 4.2 用户主链路层

保留：

- 第一轮输入
- 判断说明
- 第一轮结果
- 下一步工作区
- 第二轮优化
- 第二轮结果

价值：

- 这是最接近真实用户体验的核心路径
- 后续 UI 优化优先也应该围绕这一层

### 4.3 轻量辅助验证入口

可以保留，但建议弱化：

- `Prompt 与 LLM Draft`
- `样例运行结果`

保留方式更建议是：

- 默认折叠
- 或者收进“开发验证工具”分组

而不是和主链路同权平铺。

## 5. 首页不适合长期平铺的内容

以下区块建议逐步从首页主视图中抽离。

### 5.1 真实案例维护链

建议抽离为独立二级页，暂定可命名为：

- `案例维护台`
- 或 `Real Case Workspace`

原因：

- 字段很多
- 动作很多
- 使用频率高，但不是普通用户首轮使用入口

更适合独立承载：

- 单条录入
- 批量录入
- 写入预览
- 已写入概览
- 平台复核

### 5.2 复盘与 UI 判断链

建议抽离为另一个独立二级页，暂定可命名为：

- `验证与复盘台`
- 或 `Validation Dashboard`

原因：

- 它服务的是“下一轮做什么”的判断
- 不属于用户主流程
- 更像 PM/运营/研究台，而不是前台产品页面

更适合独立承载：

- UI 就绪度报告
- 跨批次摩擦点汇总
- 批次复盘看板

## 6. 推荐的页面分层结构

当前更合理的站内结构建议是：

### 6.1 `/`

首页，只保留：

- 产品叙事
- 主链路工作台
- 轻量开发验证入口

### 6.2 `/cases`

案例维护页，承载：

- 真实案例录入预览台
- 真实案例骨架预览
- 批量真实案例录入
- 批量写入预览
- 真实案例已写入概览
- 平台案例复核台

### 6.3 `/validation`

验证与复盘页，承载：

- UI 优化进入条件报告
- 跨批次摩擦点汇总
- 批次复盘看板

## 7. 为什么现在还不建议立刻拆页

虽然结构上已经适合拆页，但当前还不建议“先为了整齐而重构页面”，原因有 3 个：

1. 现在仍在继续收口能力边界  
如果太早拆页，容易把还没稳定的模块关系提前写死。

2. 当前更关键的是先稳定文案和产品语言  
按钮、标题、阶段命名刚开始统一，现在先把规则站稳更重要。

3. 首页仍然承担“总览工作台”的过渡作用  
在真实案例数量和复盘批次还不够多之前，保留总览页有利于整体推进。

所以更合理的顺序是：

- 先明确拆页方案
- 再做轻量分组收口
- 最后在时机成熟时真正拆页

## 8. 当前最推荐的过渡方案

在正式拆页前，首页先做这 3 步过渡最稳。

### 8.1 给首页增加“分组边界”

把首页明确分成：

- 主工作台
- 案例维护工具
- 验证与复盘工具

哪怕还在同一个页面里，也要先把层次说清楚。

### 8.2 弱化非主链路默认曝光

例如：

- `Prompt 与 LLM Draft`
- `样例运行结果`
- 部分运维工具

可以放到折叠区、次级导航或“工具区”之下。

### 8.3 为未来拆页预留命名与路由

哪怕本轮不正式实现，也建议先把这两个目标页名称固定：

- `案例维护台`
- `验证与复盘台`

这样后续代码和文档都能持续朝这个方向收敛。

## 9. 这对 UI 优化顺序意味着什么

这份结构判断也意味着，后续 UI 优化不能一次平铺全站做。

更合适的顺序是：

1. 先优化首页主链路  
也就是第一轮输入到第二轮结果这条真正面向用户的路径。

2. 再优化首页中的分组边界  
把主链路与运维区视觉上拉开。

3. 最后再分别优化二级页  
当 `/cases` 与 `/validation` 真正拆出后，再分别做更适合它们的信息架构和视觉样式。

## 10. 下一步最优动作

基于当前状态，下一步最值得推进的是：

1. 先补一版首页分组方案  
在不正式拆页的前提下，先把“主工作台 / 案例维护 / 验证复盘”三组收清楚。

2. 再决定是否做轻量导航  
如果分组之后仍然过长，再讨论页内导航或标签切换。

3. 等证据更稳定后，再正式拆 `/cases` 与 `/validation`

## 11. 当前结论

当前首页最适合继续扮演“总览工作台”，但不适合长期承担全部能力。

可以用一句话概括：

**首页保留主链路，运维与复盘能力先分组收口，等结构稳定后再拆成独立工作台。**
