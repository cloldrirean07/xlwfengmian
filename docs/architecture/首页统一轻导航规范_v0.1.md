# 首页统一轻导航规范_v0.1

## 1. 文档目的

这份文档不是为了再新增一个导航组件，而是把首页目前已经验证成功的两套轻导航模式，整理成可复用规范。

当前已经成立的两个样本是：

1. 案例维护工作台
2. 验证与复盘工作台

它们都已经完成了同一条演进链：

- 先做结构分层
- 再做默认显隐
- 再补组内快捷入口

所以现在适合把它们沉淀成统一规则，而不是继续一个工作台一个工作台地临时加入口。

## 2. 当前为什么可以开始做规范

之所以这一步现在成立，而不是更早就该做，是因为我们已经有了两个不同类型但都成立的样本：

### 2.1 案例维护工作台

特点：

- 任务密集
- 内部有明显的“单条录入 / 批量维护”分流
- 用户进入时通常带着明确任务

### 2.2 验证与复盘工作台

特点：

- 更像顺序型决策台
- 内部天然有“时机判断 -> 重复信号 -> 复盘看板”的流程
- 用户进入时通常是在做阶段复盘

这说明轻导航不是偶然适合某一块，而是开始具备复用条件。

## 3. 轻导航适用条件

当前总结下来，首页某个工作台适合接入轻导航，至少要满足 3 个条件。

### 3.1 组内存在稳定的二级结构

也就是说，这个工作台内部不能只是几个松散面板，而需要已经存在相对稳定的层级或顺序。

例如：

- 单条录入 vs 批量维护
- 时机判断 vs 重复信号 vs 复盘总览

如果组内结构还没稳定，就不适合先做导航。

### 3.2 用户进入时带着明确目标

轻导航适合的场景是：

- 用户知道自己来这组是要做某类事
- 只是需要更快到达对应层级

而不是：

- 用户还没搞清楚这组是什么

如果用户还处在“先理解这组用途”的阶段，应该先补说明和分组，不该先补导航。

### 3.3 组内长度和复杂度已经足以产生滚动摩擦

只有当组内已经开始变长，或者内部层级已经让用户产生“知道要去哪，但要找一下”的摩擦时，轻导航才有价值。

如果内容还很短，先上导航反而会让页面看起来比实际更复杂。

## 4. 当前统一结构

基于现有实现，首页轻导航当前统一由 3 层组成：

### 4.1 组头说明层

包含：

- 组标题
- 使用场景说明
- 默认显隐策略说明

作用：

- 先让用户理解这组是什么

### 4.2 组内快捷入口层

包含：

- `group-shortcut-row`

作用：

- 让用户快速跳到组内更细的层级

### 4.3 组内目标层

包含：

- 具体锚点区块

例如：

- `#single-case-flow`
- `#batch-maintenance-flow`
- `#ui-readiness-gate`
- `#cross-batch-signals-section`
- `#review-dashboard-section`

作用：

- 让快捷入口有明确落点，而不是跳到模糊区域

## 5. 当前统一交互规则

## 5.1 先有分组，再有导航

轻导航不能替代分组。

正确顺序是：

1. 先确定工作台边界
2. 再确定默认展开/收起
3. 最后才补快捷入口

如果这三步倒过来做，导航会变成在混乱结构上贴标签。

## 5.2 入口数量保持最小化

当前建议：

- 只为最稳定、最常用的组内分流点建入口

案例维护组当前只给 2 个入口：

- `先看单条录入`
- `直接去批量维护`

验证复盘组当前给 3 个入口，是因为它的三段结构都已经非常稳定。

原则是：

- 不追求覆盖所有区块
- 只覆盖最有决策价值的区块

## 5.3 入口文案优先说“去哪里”，不是“做什么组件”

推荐文案：

- `先看单条录入`
- `直接去批量维护`
- `先看时机判断`
- `再看跨批次信号`
- `直接去复盘看板`

不推荐：

- `跳转到 Section A`
- `查看模块二`

因为轻导航的目标是帮助用户建立路径，而不是暴露实现名称。

## 5.4 轻导航层级低于首页主导航

当前 `group-shortcut-row` 的视觉处理是正确的：

- 比首页 jump nav 更轻
- 比普通正文说明更强
- 不抢过工作台本身标题

这条层级关系后续要继续保持。

## 6. 为什么主链路区现在还不适合直接套这套规范

这是当前最重要的一条边界判断。

首页主链路目前暂时不建议直接套相同的轻导航模式，原因有 3 个。

### 6.1 主链路已经自带流程顺序

主链路本身已经通过：

- Hero
- workflow strip
- 第一轮输入
- 第一轮结果
- 第二轮优化

在表达一条连续流程。

这和工作台型页面不同，它本来就不是“若干相对独立区块”的集合。

### 6.2 主链路更需要减少分心

如果过早给主链路补很多快捷入口，用户可能会直接跳步骤，而不是顺着产品体验走一遍。

当前主链路的优先任务仍然是：

- 把第一次体验打磨顺

而不是让用户快速跳来跳去。

### 6.3 主链路的二级结构还没有稳定到值得导航

工作台组内的二级结构已经比较稳定，但主链路内部哪些节点值得单独成为快捷入口，目前还没有充分证据。

所以当前更适合继续用：

- 流程条
- 阶段命名
- 按钮语气

来承接主链路，而不是直接引入组内轻导航。

## 7. 当前统一结论

到这一步，可以把首页轻导航规则总结成一句话：

**只有当某个工作台已经具备稳定层级、明确进入目标、且组内滚动摩擦明显时，才适合补轻导航；主链路暂时不在这条规则内。**

## 8. 对后续 UI 讨论的门槛意义

这份规范也等于帮我们定义了：

- 什么时候能开始系统讨论首页导航

当前门槛已经满足的，是：

- 至少两个工作台已经验证轻导航有效

还没满足的，是：

- 主链路是否也需要导航
- 首页是否要统一抽成更正式的导航模式

所以现在最合理的下一步，不是直接大改导航，而是先把现有轻导航模式固定成统一规范。

## 9. 下一步建议

下一步最适合继续做的是：

1. 检查当前实现是否需要抽出统一命名与样式说明
2. 再判断首页 jump nav 和组内轻导航之间是否需要层级规则
3. 之后再进入更完整的首页统一轻导航方案讨论
