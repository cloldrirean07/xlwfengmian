# 批次复盘看板_v0.1

## 1. 本次补的是什么

新增一层独立的“批次复盘看板”。

它不是替代：

- 跨批次摩擦点汇总
- UI 优化进入条件报告

而是把这两层再收束成一个更直接的复盘入口，回答三个问题：

1. 当前最该补哪一批
2. 人工复盘是在变完整，还是还很零散
3. 离正式讨论 UI 还差什么

## 2. 为什么要单独做成一个看板

前面几轮已经补了很多证据层：

- 单批次试跑记录
- 最近人工结论覆盖状态
- 跨批次摩擦点汇总
- UI 时机判断

但如果这些信息全部散在不同面板里，真实使用时仍然有一个问题：

- 你知道很多信息
- 但不知道下一步先补哪一批

所以需要一个中间层，把“下一步优先级”显性化。

## 3. 当前架构设计

新增领域层：

- `apps/web/src/domain/review/buildBatchReviewDashboardReport.js`
- `apps/web/src/domain/review/buildBatchReviewDashboardMarkdown.js`

新增应用层：

- `apps/web/src/application/runBatchReviewDashboardPreview.js`

新增接口：

- `/api/batch-review-dashboard-preview`

## 4. 当前看板怎么构成

看板汇总三类输入：

1. 跨批次摩擦点汇总
   - 重复摩擦点类别
   - 待补人工结论批次
   - 人工完整覆盖批次

2. UI readiness
   - 当前 readiness level
   - readiness label

3. 最近批次的优先补写线索
   - 哪一批还没写
   - 哪一批只写了一半
   - 哪一批最适合作为下一步动作入口

## 5. 当前输出了什么

当前看板会直接输出：

- 当前汇总
- 当前判断
- 当前最该补的批次
- 下一步动作

这使得它更像“复盘作战面板”，而不是纯报告。

## 6. 为什么这层对 UI 讨论很关键

UI 优化往往容易提前开始。

这个看板的作用是，把讨论时机前的准备动作压缩成一句更清楚的判断：

- 现在该先补哪一批
- 补完后离 UI 讨论还有多远

这能避免团队在“知道问题很多”时，直接跳进改界面。

## 7. 当前前端挂载位置

当前挂载在：

- `apps/web/public/index.html`

作为独立区块：

- `Review Dashboard / 批次复盘看板`

这样后续如果要继续扩：

- 批次排序规则
- 覆盖趋势图
- 更明确的 UI 触发阈值

都可以在这一层继续加，而不会把已有结果区挤乱。

## 8. 当前判断

这层补完后，产品已经具备一条更清晰的推进路径：

1. 跑真实批次
2. 补人工结论
3. 看跨批次信号
4. 看复盘看板给出的下一步优先级
5. 再决定是否进入 UI 讨论

## 9. 下一步建议

下一步最有价值的是：

1. 用这块看板找出当前最该补的那一批
2. 真实补完那一批关键人工字段
3. 再跑一批新内容
4. 重新看复盘看板和 UI readiness 是否开始从 `not-ready` 走向 `near-ready`
