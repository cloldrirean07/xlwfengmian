# 复盘流程正式写回状态检查入口_v0.1

## 1. 目标

这次不是改大 UI，而是补一层流程透明度：

- 让页面里更清楚地表达“正式写回为什么还没出现”
- 让你在前端直接检查当前是否已经进入正式写回状态

## 2. 当前新增内容

前端 API：

- `previewBatchReviewManualFormalWriteReadiness`

前端交互：

- `check-manual-review-formal-write-readiness`

前端展示：

- 在复盘 follow-up 区新增 `检查正式写回状态`
- 增加一条固定提示，说明正式写回不是默认开放，而是 gated action

## 3. 为什么要补这层

现在正式写回已经是严格门控动作。

如果页面只在最后一步突然出现“执行正式写回”，会带来两个问题：

1. 你很难判断按钮是“没接上”，还是“前置条件未满足”
2. 后续自己复盘页面行为时，容易把流程门控误判成 UI 缺失

所以这里补的不是视觉改版，而是流程可解释性。

## 4. 当前页面行为

当前 follow-up 区会分成两种情况：

1. 还没走到安全写回确认：
   - 可以先点 `检查正式写回状态`
   - 页面会直接告诉你当前还卡在哪一层

2. 已完成安全写回确认：
   - 再进入 `ready-to-formal-write`
   - 这时才适合执行正式写回

## 5. 这一步和 UI 优化的关系

这一步仍然不算正式 UI 优化阶段。

它更像是：

- 先把验证流程说明清楚
- 先把门控状态暴露出来
- 避免后面在 UI 讨论时混入“其实只是流程没跑完”的噪音

## 6. 当前结论

可以把这次补充压缩成一句话：

**页面现在已经能直接解释正式写回为什么尚未开放，也能在前端主动检查当前是否已进入正式写回状态。**
