# 首页三组入口优先级与默认显隐策略接入_v0.1

## 1. 本轮为什么继续往前走

在已经完成：

- 首页分组收口
- 主链路 / 案例维护 / 验证复盘 三组边界

之后，首页虽然结构更清楚了，但还有一个问题没有解决：

- 三组虽然分开了
- 但默认曝光强度还没有拉开

这会导致首页仍然容易像一个“很多组都同样重要的总台”。

所以这轮继续做的不是新的视觉样式，而是把：

- 哪组默认展开
- 哪组默认收起
- 用户如何手动展开

真正接进页面。

## 2. 当前策略判断

基于前面已经确定的信息架构，这轮把首页三组的优先级明确成：

### 2.1 最高优先级：案例维护工作台

默认：

- 展开

原因：

- 当前项目已经在真实推进案例录入、批量回填、平台复核
- 它虽然不是普通用户主链路，但对你当前产品推进是高频工作区

### 2.2 次优先级：主链路辅助验证工具

默认：

- 收起

原因：

- `Prompt 与 LLM Draft`
- `样例运行结果`

都更偏开发验证，不需要一直占据首页主视图。

### 2.3 次优先级：验证与复盘工作台

默认：

- 收起

原因：

- UI 时机判断和跨批次复盘更像阶段性工作
- 不是每次进入首页都要优先操作的内容

## 3. 本轮实际改动

## 3.1 为三组接入 `data-workspace-group`

在 `index.html` 中，三组分别加上：

- `data-workspace-group="tools"`
- `data-workspace-group="cases"`
- `data-workspace-group="validation"`

这样页面开始具备显式分组标识，而不只是样式类名。

## 3.2 为三组补切换按钮

每个 `group-intro` 中新增：

- `button[data-workspace-group-toggle="..."]`

它负责：

- 展开这组工具
- 收起这组工具

这样首页不需要先引入复杂页签或二级导航，就能先实现轻量优先级控制。

## 3.3 为组内内容补 `group-body`

三组内部真正的工作内容现在包进：

- `group-body`

这样显隐逻辑不会影响组头说明，只会影响组内工作区。

也就是说：

- 组头始终可见
- 组体按优先级展开或收起

## 3.4 接入 `workspace-group-collapsed`

样式层新增：

- `workspace-group-collapsed`

当组被收起时：

- `group-body` 不展示

但：

- `group-intro` 仍然保留

这保证了首页仍然能表达“还有哪些工作台”，只是默认不展开。

## 3.5 在 `createApp.js` 中接入初始化与切换逻辑

新增：

- `syncWorkspaceGroupToggle(groupName, expanded)`

它负责统一处理：

- 分组 class 切换
- `aria-expanded`
- 按钮文案

当前初始化策略是：

- `tools` -> `false`
- `cases` -> `true`
- `validation` -> `false`

## 3.6 修正真实案例表单 DOM 选择器

上一轮已经把：

- 首页锚点 `#real-case-form`

和：

- 真实案例录入表单

做了语义拆分。

所以这轮同步修正 `dom.js`：

- `realCaseForm: query("#real-case-intake-form")`

避免继续拿到分组锚点节点而不是表单节点。

这一步不是附带修修补补，而是保证案例维护链在分组收口后仍然可用。

## 5. 本轮没有做什么

这轮没有做：

- 正式拆成 `/cases` 或 `/validation` 路由
- 引入页签式导航
- 改业务接口
- 改任何领域层逻辑

因为当前这轮的任务仍然是：

- 先让首页显隐优先级更合理

而不是提前进入大范围重构。

## 8. 对后续 UI 优化的意义

这一步做完后，后续 UI 优化的顺序更清楚了：

1. 继续打磨主链路体验
2. 再收首页分组的视觉权重和组内导航
3. 最后再决定什么时候正式拆成独立工作台

也就是说，这轮是把“先做结构，后做视觉”的节奏再往前推了一步。
