# 人工复盘待补任务导出后读回识别_v0.1

## 1. 目标

前一轮我们已经让人工复盘待补任务可以导出到 Obsidian。

这次要继续解决的问题是：

- 导出之后，系统怎么知道这份草稿有没有被填写过

如果没有这层读回识别，链路仍然会停在：

- 可以导出
- 但系统不知道你有没有真的补

所以这次补的是：

- 人工复盘待补任务草稿的读回识别能力

## 2. 当前接入思路

这次没有直接把填写内容自动写回真实批次试跑记录，而是先补一层更基础的能力：

1. 读取最新导出的任务草稿
2. 解析其中已填写的关键字段
3. 判断当前是否已经有人工输入

这一步更稳，因为它先解决“识别是否填写”，再考虑后面的自动回流。

## 3. 当前新增产物

领域层：

- `parseBatchReviewManualTaskCardNote.js`

应用层：

- `loadLatestBatchReviewManualTaskCardStatus.js`

接入位置：

- `runBatchReviewManualTaskCardPreview.js`

## 4. 当前识别的字段

当前会识别：

- `目标批次`
- `最卡环节`
- `问题类型判断`
- `最该前置模块`
- `UI 时机判断`
- `这一批最重要的一句判断`
- `补完后最想重跑验证的点`
- `是否更接近进入首页系统 UI 讨论`

其中最重要的是前 4 项核心人工判断字段。

## 5. 当前能判断什么

系统现在可以得到：

- 最新导出的任务草稿路径
- 对应批次标签
- 是否已经有人工输入
- 已填写字段列表
- 已填写字段数量

这意味着后续不再只是“假设用户可能填了”，而是开始有实际状态依据。

## 6. 为什么这一步重要

这一步是整条链真正开始闭环的关键过渡层。

因为现在项目已经具备：

1. 发现待补批次
2. 生成待补任务卡
3. 导出到 Obsidian
4. 识别这份草稿有没有被填写

后面如果再继续做自动回流或再判断触发，就会更自然。

## 7. 当前结论

可以把这一步压缩成一句话：

**人工复盘待补任务现在不只是能导出，系统也开始能识别这份草稿是否已经被实际填写。**
