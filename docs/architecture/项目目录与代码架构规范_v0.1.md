## 3. 顶层目录职责

### 3.1 `apps`

承载真正可运行的产品代码。

- `apps/web`
  - 当前 MVP 主应用。
  - 承载输入表单、方向分析、二轮 refinement、报告生成、Obsidian 导出等能力。
- `apps/admin`
  - 预留管理后台。
  - 后续可放规则管理、案例审核、反馈词审核、实验看板。
- 未来预留：`apps/api`
  - 如果后续需要独立接口层，可新增此目录。
  - 负责模型调用、规则编排、案例检索、图片推荐接口。

### 3.2 `data`

承载结构化业务数据，避免直接把关键规则硬编码在页面层。

- `data/rules`
  - 封面效果方向规则、反馈词映射、判断信号。
- `data/cases`
  - 样例、平台案例、真实案例结构化数据。
- `data/feedback`
  - 用户反馈词、人工复核沉淀、误判样本整理源数据。
- `data/experiments`
  - A/B 验证、问卷结果、阶段实验原始记录。

### 3.3 `docs`

承载代码侧文档，不替代 Obsidian，而是作为工程内可版本管理的说明。

- `docs/product`
  - 产品定位、用户问题、价值主张、边界说明。
- `docs/prd`
  - 版本化 PRD、MVP 范围、输入输出链路。
- `docs/research`
  - 案例调研、竞品拆解、封面方法论来源。
- `docs/architecture`
  - 代码架构、数据结构、模块分层、技术方案。
- `docs/operations`
  - 每轮推进记录、实验日志、同步记录。

### 3.4 `prototypes`

承载原型与交互验证材料。

- `prototypes/wireframes`
  - 低保真结构。
- `prototypes/hi-fi`
  - 高保真页面或视觉探索。
- `prototypes/flows`
  - 用户链路、状态流、操作流程。
- `prototypes/tests`
  - 原型验证记录、可用性观察。

### 3.5 `assets`

承载非结构化视觉素材。

- `assets/raw`
  - 原始图片、待整理参考图。
- `assets/references`
  - 广告案例、平台封面灵感参考。
- `assets/screenshots`
  - 页面截图、平台截图、过程截图。
- `assets/generated`
  - AI 生成图、实验产出图。
- `assets/exports`
  - 对外展示截图或作品集配图。

### 3.6 `outputs`

承载程序运行后的结果，不把这些临时产物直接混入源码目录。

- `outputs/case-runs`
  - 每个样例或真实案例的运行结果。
- `outputs/reports`
  - 汇总报告，如误判样本导出、规则修订任务单。
- `outputs/previews`
  - 页面预览、导出预览、中间产物。

### 3.7 `scripts`

承载辅助脚本，不和业务域逻辑混写。

- `scripts/setup`
  - 初始化、脚手架、目录准备。
- `scripts/sync`
  - 与 Obsidian 的同步、导出、回写。
- `scripts/analysis`
  - 批量分析、批量校验、离线处理。

## 4. 当前主应用 `apps/web` 的代码分层

### 4.1 推荐分层

当前代码已经在朝下面这套结构收敛，后续应继续保持：

- `src/application`
  - 编排具体用例。
  - 例如：创建分析会话、创建 refinement 会话、运行 case flow。
- `src/domain`
  - 业务规则核心。
  - 例如：封面方向判断、反馈映射、报告构造、规则修订任务生成。
- `src/infrastructure`
  - 与外部系统交互。
  - 例如：规则文件加载、Obsidian 根目录解析、LLM provider 适配。
- `src/shared`
  - 纯工具能力。
  - 例如：文件读写、通用格式化、基础 helpers。
- `src/server`
  - HTTP 服务入口与路由。

### 4.2 为什么这样拆

- `application` 负责“调度流程”，不是堆业务细节。
- `domain` 负责“产品能力本身”，方便以后替换模型或前端形态。
- `infrastructure` 负责“接外部资源”，避免 Obsidian、文件系统、LLM 耦合进核心规则。
- `shared` 保持轻量，只放通用工具，避免变成杂物间。

## 5. 后续新增代码时的放置规则

### 5.1 新增规则

如果是“封面效果方向”“反馈词映射”“判断信号”之类规则：

- 优先放到 `data/rules`
- 加载逻辑放 `src/infrastructure/rules`
- 解释、匹配、应用逻辑放 `src/domain`

### 5.2 新增实验链路

如果是“人工复核”“误判样本导出”“规则修订任务单”这类链路：

- 生成报告逻辑放 `src/domain`
- 脚本入口放 `scripts`
- 程序输出落 `outputs/reports`
- 对应说明文档追加到 `docs/architecture` 或 `docs/operations`

### 5.3 新增页面能力

如果是“输入页”“结果页”“二轮优化页”“案例后台”：

- UI 页面放 `apps/web/src`
- 页面编排不要直接写死规则，走 `application -> domain -> infrastructure`

## 6. 与 Obsidian 的关系

Obsidian 是产品知识库与推进中枢，代码仓库是工程实现中枢。

推荐分工：

- Obsidian
  - 产品定义
  - 用户洞察
  - 规则库手工沉淀
  - 实验记录
  - 案例评审
- 代码仓库
  - 可执行逻辑
  - 可测试规则
  - 可复用数据结构
  - 自动化导出与同步

原则是：高频需要版本控制、测试、自动运行的内容，逐步从纯文档沉淀到代码仓库中。

## 7. 当前阶段最合理的开发顺序

### 第一阶段

- 固化项目目录与代码边界。
- 跑通 `输入 -> 首轮分析 -> 二轮 refinement -> 人工复核 -> 误判导出 -> 规则修订任务单`。

### 第二阶段

- 把 5 类封面效果方向做成稳定规则输入。
- 把反馈词映射、误判样本、判断信号清单逐步结构化。
- 增加真实案例批量评审与回填。

### 第三阶段

- 接入真正的模型调用。
- 增加图片方向推荐、标题建议、多轮优化。
- 再决定是否拆出 `apps/api` 和 `apps/admin`。
