# 方向信号接入二轮解释与修订链路 v0.1

## 1. 本轮解决的问题

上一轮已经把 5 类封面效果方向的判断信号接入了首轮分析与前端展示。

但如果这些信号只停留在首轮卡片里，会有一个明显断层：

- 二轮解释不知道首轮为什么判成这个方向
- 误判样本导出只能看到“原映射错了”，看不到“原方向为什么会成立”
- 规则修订任务单只能改反馈词，缺少更上游的方向判断依据

所以这轮的目标，是把 `directionSignalChecklist` 继续接到后面的复核链路。

## 2. 本轮接入位置

### 2.1 二轮解释记录

文件：

- `src/domain/refinement/buildRefinementExplanationMarkdown.js`

新增内容：

- `## 2.1 首轮方向判断依据`
- 首轮方向标签
- 首轮方向类型
- 首轮命中信号
- 首轮边界提醒

这样当你人工复核“这次反馈映射是否合理”时，不需要回头再去翻第一轮结果。

### 2.2 误判样本导出

文件：

- `src/domain/refinement/buildReviewedMisclassifiedExportReport.js`
- `src/domain/refinement/buildReviewedMisclassifiedExportMarkdown.js`

新增导出字段：

- `sourceDirectionLabel`
- `sourceDirectionType`
- `sourceMatchedSignals`
- `sourceBoundaryRules`

作用：

- 不只知道“系统原来判成了什么映射”
- 还知道“系统原来为什么会觉得这个方向成立”

### 2.3 规则修订任务单

文件：

- `src/domain/refinement/buildRuleRevisionTaskSheetReport.js`
- `src/domain/refinement/buildRuleRevisionTaskSheetMarkdown.js`

新增聚合字段：

- `sourceDirectionLabels`
- `sourceMatchedSignals`
- `sourceBoundaryRules`

这让任务单不只是在改一个关键词，而是在告诉你：

- 哪类方向最容易连带误判
- 原先常见的方向信号是什么
- 哪些边界规则可能需要进一步前置或强调

### 2.4 端到端样例记录

文件：

- `src/domain/cases/buildCaseRunMarkdown.js`

新增：

- 每张卡片的命中信号
- 每张卡片的边界提醒

这样 case-run 记录本身也更适合作为方法论样本。

## 3. 为什么这一步重要

这一步的意义，不是“让 Markdown 更长”，而是让系统出现真正的回流闭环：

1. 首轮方向判断给出方向与信号
2. 二轮解释基于反馈进行修正
3. 人工复核发现误判
4. 误判导出把“原映射 + 原方向信号”一起保留
5. 规则修订任务单据此反推该补哪类词、哪类边界、哪类方向信号

这样你做的就不再只是一个“会给建议的页面”，而是一个可持续学习的规则系统。

## 5. 当前残留

目前历史 `case-runs` 结果里仍混有旧快照。

这意味着：

- 新代码已经支持方向信号穿透
- 但旧样例需要通过 `run:case` 重新生成一次，报告里才会完全使用新字段

这不是架构问题，而是规则升级后的样例复跑问题，后续应视为常规流程。

## 6. 下一步建议

### 6.1 建立“规则升级后复跑样例”的固定流程

每次规则层升级后，至少自动复跑：

- `sample-001`
- `real-001`
- 当前用于误判导出的关键样例

### 6.2 把方向边界提醒也前置进反馈映射

例如：

- “悬念不能变成标题党”
- “冲突不能脱离内容硬造反差”

这些边界规则未来可以进一步参与二轮解释与默认兜底判断。

### 6.3 继续接真实案例标注

下一步最值得做的是把真实案例或平台案例映射到：

- 方向信号
- 常见误判
- 修订任务

这样规则系统会越来越像一个真实可迭代产品。
