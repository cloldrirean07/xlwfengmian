# 当前 Web 应用代码模块地图 v0.1

## 1. 文档目的

这份文档只回答三个问题：

1. 当前 `apps/web` 已经拆成了哪些稳定层级
2. 每一层分别在承接哪类产品能力
3. 后续继续写代码和讨论 UI 时，应该优先改哪一层，不该混改哪一层

它的作用不是重复介绍全部业务，而是把“现阶段代码已经长成什么样”说清楚。

## 3. 当前代码顶层结构

`apps/web/src` 当前已经拆成五层：

- `application`
  - 用例编排层
  - 负责把输入、规则、导出、状态检查串成可执行流程
- `domain`
  - 业务能力核心层
  - 负责方向判断、卡片生成、反馈映射、复盘写回、案例规则等产品逻辑
- `infrastructure`
  - 外部资源接入层
  - 负责规则加载、案例文件读写、Obsidian 根目录解析、LLM provider 接口准备
- `server`
  - HTTP 入口层
  - 负责把前端请求路由到对应的 application 用例
- `shared`
  - 通用基础层
  - 负责文件系统、HTTP 响应、文本工具等公共能力

这套分层已经满足继续扩展，不需要回退成单文件或页面直连规则的结构。

## 4. `domain` 现有子域职责

### 4.1 `analysis`

负责把用户输入整理成可用于方向判断的结构。

- 典型能力：
  - 抽取输入字段
  - 推断素材建议
  - 排序方向候选

适合继续放入：

- 输入标准化
- 内容主题抽取
- 素材类型初步判断

### 4.2 `cards`

负责把判断结果组织成用户可以直接阅读的候选方向卡。

- 典型能力：
  - 首轮结果卡生成
  - 图片方向候选生成
  - 候选图片策略排序

适合继续放入：

- 三个封面方向的结构模板
- 标题建议和构图建议的统一输出骨架

### 4.3 `directions`

负责方向规则与信号清单。

- 典型能力：
  - 方向目录
  - 方向信号目录
  - 方向判断清单

这是后续“5 类封面效果方向体系”的直接代码承载位。

### 4.4 `effects`

负责封面效果相关的抽象标签与效果目录。

适合继续放入：

- 风险损失感
- 结果承诺感
- 好奇悬念感
- 反差冲突感
- 信息清单感

### 4.5 `refinement`

负责第二轮反馈、用户修订意图和结果再组织。

- 典型能力：
  - 反馈映射解释
  - 第二轮结果卡
  - 规则修订任务单
  - 误判样本导出

这是“用户说我想更炸一点 / 更像热门内容 / 不要太营销号”这类反馈继续结构化的核心位置。

### 4.6 `review`

负责批次复盘、人工任务卡、安全写回预览、正式写回准备等闭环能力。

这是当前工程里最重的一段链路，也是为什么现在还不适合过早做大面积 UI 重写的核心原因。

### 4.7 `cases`

负责平台案例、真实案例、批次记录、回填工作单、维护看板等。

它让这个项目已经不只是一个“封面灵感 demo”，而是一个可持续积累案例资产的系统。

### 4.8 `workspace`

负责工作区建议、动作建议与工作台中间状态表达。

这层未来会直接影响 UI 的“下一步建议区”和“推荐动作区”设计。

### 4.9 `ui`

负责 UI 优化 readiness 报告与相关判断材料。

这说明系统已经开始具备“先收集证据，再决定是否优化 UI”的产品意识，而不是纯凭感觉改页面。

## 5. `infrastructure` 现有职责

### 5.1 `rules`

- 规则目录加载

后续如果要把更多规则表、案例标签、反馈词表继续结构化，优先延展这里。

### 5.2 `cases`

- 案例索引加载
- 真实案例路径解析
- 脚手架保存

### 5.3 `obsidian`

- Obsidian 根目录解析
- 平台案例笔记读取

这层是“代码仓库”和“Obsidian 知识库”之间的关键桥。

### 5.4 `llm`

- LLM 请求上下文
- Provider 创建
- 请求校验

说明系统已经为后续接真正模型服务预留好了接口位置。

## 6. `application` 当前承担什么

`application` 层当前主要承担四类动作：

1. 运行分析或预览
2. 生成导出预览
3. 写出到 Obsidian
4. 读取最近状态并回显到工作台

这意味着后续写功能时，优先顺序应该是：

- 先在 `domain` 把规则或结果结构定义清楚
- 再在 `application` 串成流程
- 最后在 `server` 和前端接入口

不要反过来从 UI 先写死。

## 7. 这套结构对 UI 优化意味着什么

当前已经可以做两类 UI 工作：

- 轻量结构整理
  - 区块命名
  - 分组层级
  - 高频动作前置
  - 结果阅读顺序优化
- 局部体验优化
  - 更清楚的按钮语气
  - 更明确的下一步提示
  - 更容易比较三种方向

当前还不适合立刻做的，是：

- 全站视觉风格重写
- 完整信息架构推翻重做
- 在主链路仍会变动时大量抽 UI 皮肤组件

原因不是 UI 不重要，而是当前 `review`、`cases`、`workspace` 仍在继续收口，过早全面改视觉会反复返工。

## 8. 后续继续写代码时的优先顺序

### 第一优先

继续收口 `domain/directions`、`domain/effects`、`domain/refinement`

目标：

- 把封面方向体系、反馈映射和第二轮优化规则再做稳一点

### 第二优先

继续收口 `domain/cases`、`domain/review`、`application`

目标：

- 让真实案例沉淀、人工复盘和写回链路更清楚

### 第三优先

在前两项更稳后，再集中讨论系统级 UI 优化

目标：

- 决定首页是否拆页
- 决定手机端与桌面端是否分路径
- 决定第一轮、第二轮、案例维护是否拆成更明确的阶段流

## 9. 当前结论

当前最合理的推进顺序不是“先重做 UI”，而是：

1. 继续把规则层和案例闭环层写扎实
2. 让 Obsidian 导出与状态回看继续稳定
3. 在真实高频路径更清楚之后，再做系统性 UI 方案讨论

一句话总结：

**代码架构已经足够支撑继续开发，下一步重点是继续稳住规则与案例闭环，而不是急着做大范围视觉翻修。**
