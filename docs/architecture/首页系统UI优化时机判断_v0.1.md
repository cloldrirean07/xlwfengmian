# 首页系统UI优化时机判断_v0.1

## 1. 文档目的

这份文档不是再重复“UI 以后再做”，而是要基于当前项目的真实证据，回答一个更具体的问题：

- 现在首页是不是已经适合进入系统 UI 优化讨论
- 如果还不到，差的到底是哪一层证据
- 在正式进入系统 UI 优化前，当前最适合继续做什么

这份判断会承接已有几类文档：

- `docs/prd/UI优化进入条件与分期范围_v0.1.md`
- `docs/architecture/UI优化进入条件报告生成与导出_v0.1.md`
- `docs/architecture/首页页面分层与拆页建议_v0.1.md`
- `docs/architecture/首页主导航与组内轻导航层级规则_v0.1.md`

也就是说，这份文档不是原则说明，而是“基于当前状态的阶段判断”。

## 2. 当前判断结论

当前首页状态更适合定义为：

**已经接近可以进入系统 UI 讨论，但还不建议立刻启动全量首页 UI 改版。**

更准确地说：

- 当前已经可以继续做轻量 UI 收口
- 当前还不适合直接进入大范围视觉方案或正式拆页实施
- 当前最应该补的是“人工复盘判断”这层证据，而不是先补更多视觉表达

## 3. 当前判断依据

证据来源：

- `apps/web/outputs/ui-readiness/ui-readiness-report.json`
- `apps/web/outputs/batch-run-friction-summary/batch-run-friction-summary.json`

从当前代码侧产出的就绪度报告看，首页 UI 时机状态为：

- `readinessLevel`: `near-ready`
- `readinessLabel`: `接近可以进入 UI 讨论`

当前已满足的检查：

- 至少 2 批批量工作单导出
- 至少 2 批批量工作单读回确认
- 至少 2 批真实批次试跑记录
- 至少 1 批试跑记录读回确认
- 跨批次重复摩擦点信号至少达到 `emerging-signal`

当前未满足的关键检查：

- 至少 1 批关键人工判断字段补完整

这意味着：

- 结构性证据已经开始成立
- 重复摩擦点已经开始出现
- 但“人到底卡在哪、是不是 UI 问题”这层人工判断仍然为空

## 4. 为什么当前还不能直接开系统 UI 方案

当前不是没有 UI 问题，而是还没到“可以放心开大改”的程度。

主要原因有 3 个。

### 4.1 缺少人工复盘结论

当前两批试跑记录都还没有补齐这些关键字段：

- `最卡环节`
- `问题类型判断`
- `最该前置模块`
- `UI 时机判断`

这会导致一个很大的风险：

- 我们看到了一些重复摩擦点
- 但还不能稳定判断这些摩擦点到底更像输入问题、规则问题，还是展示问题

如果这时直接开 UI 改版，容易把前面的产品问题误判成界面问题。

### 4.2 当前最高优先摩擦点仍然偏输入结构

跨批次摩擦点里，目前优先级最高的是：

- `输入准备与案例结构`
- `补写建议与优先顺序`

这说明首页当前最应该继续收口的，不是先换一套更“完整”的视觉皮肤，而是继续确认：

- 输入是不是太重
- 用户是不是缺少必要素材上下文
- 系统给的下一步动作是否足够明确

也就是说，问题更偏“产品组织方式”，还不完全是“视觉表达方式”。

### 4.3 首页虽然已经开始分层，但主链路仍然在继续收口

当前首页已经完成：

- 主导航与组内轻导航分层
- 三组工作区显隐策略
- 案例维护工作台内部双层分流
- 验证与复盘工作台内部快捷入口

这些都说明首页结构已经更清楚了。

但这仍然更像是：

- 在给系统 UI 讨论做准备

而不是：

- 首页整体信息架构已经完全稳定

所以现在更适合继续做“方向明确的小收口”，而不是直接做“全面改版”。

## 5. 当前已经可以做的 UI 工作

虽然还不建议开全量 UI 改版，但当前并不是“完全不要碰 UI”。

当前适合继续做的，是下面这 3 类工作。

### 5.1 继续做轻量层级整理

例如：

- 首页主导航与组内轻导航的层级强化
- 组标题、阶段标题、按钮语气统一
- 默认展开/收起策略继续压缩噪音

这类工作风险低，而且会直接帮助后续判断主链路是否清楚。

### 5.2 继续打磨主链路阅读顺序

例如：

- 第一轮结果区是否更容易扫读
- 第二轮入口是否更像自然下一步
- 工作区建议区是不是过于“后台感”

这类优化仍然属于信息结构和节奏优化，不属于大规模视觉返工。

### 5.3 继续为未来拆页做证据准备

例如：

- 首页哪些区块长期应该保留
- 哪些区块最终要抽离到 `cases` 或 `validation`
- 哪些工作区是真高频，哪些是验证驾驶舱

这类判断越早清楚，后面真正做 UI 和页面拆分时越不会返工。

## 6. 当前暂时不建议做的 UI 工作

当前不建议优先做的是：

- 系统级视觉风格重做
- 首页大范围重新排版
- 直接开始正式拆页实施
- 为尚未稳定的区块做高保真皮肤
- 大量补动画、氛围视觉和营销化包装

原因不是这些不重要，而是它们都依赖更稳定的前置判断。

## 7. 下一步的最优推进顺序

如果按当前项目状态排优先级，下一步最适合这样推进：

1. 补至少 1 批完整人工复盘字段
2. 重新生成 `UI readiness` 报告
3. 再看 `near-ready` 是否提升为更稳定的 `near-ready` 或进入 `ready`
4. 如果人工结论开始稳定重复，再开首页系统 UI 讨论
5. UI 讨论时先谈首页主链路，不先谈整站统一美化

这里最关键的一点是：

**下一次正式 UI 讨论，应该建立在“人工已经明确说出最卡点”的基础上，而不是只基于代码侧汇总信号。**

## 8. 当前阶段的一句话判断

可以把当前状态压缩成一句话：

**首页已经进入“UI 讨论前的最后一小段准备期”，现在适合继续做轻量结构优化，但还不适合直接启动全量系统 UI 改版。**

## 9. 对你当前工作的直接建议

如果站在产品经理推进真实产品的角度，当前你最该做的不是先纠结“首页最终长什么样”，而是：

1. 继续用真实案例跑
2. 把人工复盘字段补起来
3. 让“最卡环节”和“是否属于 UI 问题”开始有连续记录
4. 再和我一起开系统 UI 优化讨论

这样后面的 UI 讨论会更像产品决策，而不是审美猜测。
