# 真实案例回填导出后读回确认 v0.1

## 1. 本次改动解决什么问题

上一轮已经支持：

- 页面确认导出真实案例回填工作单到 Obsidian

但当时的返回结果只说明“已经执行写入”，还缺一层更强的确认：

- 写入后的目标文件是否真的存在并可读
- 读回内容是否和预期草稿一致

这次补的是：

**导出后立即读回目标文件，并把读回确认结果返回给页面。**

## 2. 为什么要补读回确认

仅仅显示“已导出”还不够稳，因为页面层看到的是动作成功，不一定等于目标文件内容完全正确。

补读回确认后，页面可以直接知道：

- 是否确实读回成功
- 首行标题是否正确
- 文件长度是否合理
- 写入内容是否与预期完全一致

这会让“确认导出”从弱提示，升级为更可验证的闭环。

## 3. 代码层改动

### 3.1 扩展共享文件能力

更新：

- `src/shared/fileSystem.js`

新增：

- `readTextFile`

这样后续其他导出动作如果也需要写后读回，不需要重复直接依赖 `fs/promises`。

### 3.2 导出用例补充读回校验

更新：

- `src/application/exportRealCaseFillSheetToObsidian.js`

导出逻辑现在会：

1. 生成预期草稿内容
2. 写入目标路径
3. 立刻读回目标文件
4. 生成 `readback` 结果

当前 `readback` 字段包括：

- `ok`
- `persistedHeading`
- `persistedLength`
- `matchedExpectedContent`

## 4. 前端表现

更新：

- `public/app/renderers.js`

导出结果卡现在除了显示：

- 导出路径
- 代码底稿
- 生成日期

还会额外显示：

- 读回确认状态
- 读回首行
- 读回长度

这样页面不只是在说“写了”，而是在说“写了并且读回确认了”。

## 5. 为什么这一步很重要

当前项目正处于“工作台结果逐步接近真实知识库落地”的阶段。

在这个阶段，最容易出问题的不是逻辑跑不跑，而是：

- 页面看起来成功
- 实际文件状态不明确

读回确认补上后，这条链路更接近真实后台系统常见的写后校验方式。

## 6. 当前结论

现在单案例真实案例回填导出链已经形成：

1. 预览工作单
2. 预览 Obsidian 草稿
3. 确认导出
4. 写后读回确认

这说明当前链路已经不仅仅是“功能存在”，而是开始具备更可验证的工程可靠性。
