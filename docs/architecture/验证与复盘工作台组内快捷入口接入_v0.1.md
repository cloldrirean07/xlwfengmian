# 验证与复盘工作台组内快捷入口接入_v0.1

## 1. 本轮为什么继续扩一组

在案例维护工作台已经接入组内快捷入口之后，下一步最自然的验证不是直接做全站导航，而是先看：

- 这种轻导航模式
- 是否也适用于验证与复盘工作台

因为只有至少两个高价值工作台都成立，后面再讨论首页统一轻导航，才有足够依据。

## 2. 本轮判断基础

验证与复盘工作台内部本来就有一条非常清晰的顺序：

1. `UI 优化进入条件报告`
2. `跨批次摩擦点汇总`
3. `批次复盘看板`

这三块不是随机并列，而更像：

- 先判断时机
- 再看重复证据
- 最后看收口后的复盘总览

所以它非常适合接入最小快捷入口。

## 3. 本轮实际改动

## 3.1 在验证与复盘组头部新增快捷入口

在 `group-intro` 中新增：

- `group-shortcut-row`

当前包含 3 个入口：

- `先看时机判断`
- `再看跨批次信号`
- `直接去复盘看板`

## 3.2 为内部区块补更清晰的锚点

本轮使用或新增：

- `id="ui-readiness-gate"`
- `id="cross-batch-signals-section"`
- `id="review-dashboard-section"`

这样三段核心内容都能被直接跳转到。

## 3.3 为什么这组用 3 个入口

和案例维护组不同，验证与复盘组内部本身就是三段结构都相对稳定：

- 第一段回答“现在能不能开始谈 UI”
- 第二段回答“最常重复的问题是什么”
- 第三段回答“当前整体复盘结论是什么”

所以它适合一次给出三类入口，而不是只给两个。

## 4. 涉及文件

- `apps/web/public/index.html`

样式层不需要新加结构，因为：

- 直接复用了案例维护工作台已经验证过的 `group-shortcut-row`

这本身也是一个正向信号，说明当前轻导航模式已经开始具备复用性。

## 5. 为什么这一步重要

这一步的意义不只是“又多了几个锚点”，而是它帮助我们验证：

- 轻导航不是只适合案例维护组
- 它也适合阶段性强、内部顺序明确的验证复盘组

如果这两个组都成立，后面就可以更有把握地讨论：

- 首页是否需要统一轻导航
- 哪些组适合统一模式
- 哪些组仍然只适合分组收口

- 哪些组只保留分组和显隐就够了

这已经很接近真正系统化 UI 讨论的前一步。
