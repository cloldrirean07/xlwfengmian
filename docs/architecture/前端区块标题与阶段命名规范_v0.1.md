# 前端区块标题与阶段命名规范_v0.1

## 1. 文档目的

这份文档要解决的不是“标题怎么写更好看”，而是前端页面里的区块标题、阶段命名、提示语气如何保持同一套产品语言。

在当前项目里，按钮语气已经开始统一，但如果区块标题仍然各说各话，页面仍然会显得像多个 demo 拼在一起，而不是一个在持续收敛的真实产品。

这份规范的目标有 3 个：

1. 让用户一眼看懂当前页面每个区块是“主链路”“验证链路”还是“运维链路”
2. 让阶段命名能稳定表达“现在在哪一步、下一步是什么”
3. 为后续 UI 优化提供统一的文案基线，而不是一边改视觉一边重新想名字

## 2. 当前要解决的问题

从现有页面看，已经出现了 3 类命名并存的情况：

- 面向用户任务的命名：`第一轮输入`、`第二轮优化`
- 面向系统内部机制的命名：`Decision Frame`、`Branch Workspace`
- 面向运维动作的命名：`真实案例录入预览台`、`批次复盘看板`

这些命名本身不一定错，但如果没有规则，会出现两个问题：

1. 用户不容易分清哪些区块属于真实使用主链路，哪些属于内部验证和维护区
2. 页面标题会时而像产品功能，时而像研发模块，时而像运营工具

所以这份规范的重点，不是让所有标题都完全一样，而是明确不同区块应该说哪一种语言。

## 3. 规范范围

当前规范覆盖：

- Hero 区与 workflow strip
- 主链路工作台
- 第一轮到第二轮相关区块
- Prompt / LLM 草稿辅助区
- 真实案例录入与批量回填区
- UI 时机判断、摩擦点汇总、复盘看板

暂不覆盖：

- API 字段命名
- 文档目录命名
- Obsidian 文件命名

因为这份规范只针对前端展示层。

## 4. 区块命名的 3 层结构

当前前端区块命名建议拆成 3 层：

1. `section-kicker`
2. 主标题
3. 辅助说明

职责分别如下。

### 4.1 `section-kicker`

适合承担：

- 当前区块属于哪条链路
- 当前区块是第几阶段
- 当前区块的英文或抽象标签

当前适合的表达方式：

- `MVP Workbench`
- `First Round`
- `Second Round`
- `Branch Workspace`
- `Decision Frame`

使用规则：

- kicker 更像“类目标签”，不是完整说明句
- 尽量短，不超过 2 到 3 个词
- 可以允许少量英文，用来增强信息分层，但不要让英文承担真正的业务说明

### 4.2 主标题

适合承担：

- 用户当前真正要做的事
- 当前区块的主要输出或动作

推荐特点：

- 中文优先
- 让用户直接看懂“这是干什么的”
- 不使用内部术语堆叠

例如：

- `第一轮输入`
- `系统当前怎么判断`
- `第一轮方向结果`
- `下一步工作区`
- `第二轮优化`
- `第二轮优化结果`

### 4.3 辅助说明

适合承担：

- 当前区块为什么存在
- 这一轮先验证什么
- 用户最少需要提供什么

它可以放在：

- 主标题下方
- 区块内第一段说明
- callout 或 highlight 中

原则是：

- 解释“为什么”
- 不重复标题本身
- 不把细碎字段说明都堆到标题旁边

## 5. 不同区块该说什么语言

## 5.1 主链路区块：说“用户任务语言”

主链路包括：

- Hero 主价值
- 第一轮输入
- 第一轮结果
- 下一步工作区
- 第二轮优化
- 第二轮结果

这些区块标题应该优先说：

- 用户在做什么
- 系统接下来会产出什么

推荐语言：

- `第一轮输入`
- `第一轮方向结果`
- `下一步工作区`
- `第二轮优化`
- `第二轮优化结果`

不推荐写成：

- `分析模块`
- `方向推理层`
- `结果生成引擎`

因为这些更像内部实现，而不是产品界面。

## 5.2 判断辅助区块：说“机制解释语言”

这类区块不是让用户直接完成动作，而是解释系统为什么这么判断。

例如：

- `系统当前怎么判断`
- `Decision Frame`

它们更适合说：

- 系统先看什么
- 系统如何缩小方向
- 为什么不是直接给终稿

这类区块可以稍微抽象一点，但主标题仍然要让普通用户看懂，不建议只有英文。

## 5.3 运维与验证区块：说“验证与管理语言”

例如：

- `真实案例录入预览台`
- `批量真实案例录入`
- `UI 优化进入条件报告`
- `跨批次摩擦点汇总`
- `批次复盘看板`

这类区块不是面向第一次使用的普通用户，而更像团队内部推进产品时要用的验证面板。

所以这类区块允许更偏“操作台 / 看板 / 报告 / 汇总”的命名，但应满足两个条件：

1. 一看就知道它不是主使用链路
2. 名字里要明确它是在“录入 / 预览 / 汇总 / 导出 / 复盘”哪一类动作

## 6. 阶段命名规范

当前产品最重要的是主链路阶段语言统一。

建议固定成下面这套顺序：

1. `第一轮输入`
2. `第一轮方向结果`
3. `下一步工作区`
4. `第二轮优化`
5. `第二轮优化结果`

这样做的原因是：

- `第一轮` 和 `第二轮` 已经成为当前产品认知骨架
- `方向结果` 比单说“结果”更具体
- `下一步工作区` 明确它不是独立模块，而是承接首轮后的决策空间

当前不建议随意混用的说法：

- `首轮判断`
- `第一次输出`
- `优化二区`
- `结果二`

因为这会让不同阶段像临时取名。

## 7. Hero 与流程条的命名规则

Hero 和 workflow strip 属于“产品总叙事层”，不属于具体表单区块。

建议规则：

- Hero 主标题负责讲最终价值
- Hero 辅助文案负责讲这版验证边界
- workflow strip 负责讲当前流程拆解

当前这套表达是合理的：

- Hero：`把内容想法，先变成 3 个有点击逻辑的封面方向`
- 流程条：
  - `输入内容与素材情况`
  - `系统判断点击机制`
  - `输出 3 个方向与配图路径`

这三条的语法结构也值得继续保留：

- 动词 + 对象
- 每一条都明确一个阶段动作

## 8. 当前页面推荐口径

基于当前页面，建议后续继续沿用以下区块标题。

### 主链路

- `第一轮输入`
- `系统当前怎么判断`
- `第一轮方向结果`
- `下一步工作区`
- `第二轮优化`
- `第二轮优化结果`

### 辅助输出

- `Prompt 与 LLM Draft`
- `样例运行结果`

### 验证与运维

- `真实案例录入预览台`
- `真实案例骨架预览`
- `批量真实案例录入`
- `批量写入预览`
- `UI 优化进入条件报告`
- `跨批次摩擦点汇总`
- `批次复盘看板`
- `真实案例已写入概览`
- `平台案例复核台`

## 9. 新增区块前的判断清单

新增前端区块标题前，先回答这 5 个问题：

1. 这个区块属于主链路、判断辅助，还是运维验证
2. 主标题是否直接说清楚用户要做什么或会看到什么
3. `section-kicker` 是否只是标签，而不是重复主标题
4. 这个命名是否混入了太多内部术语
5. 同一层级相邻区块的命名语法是否一致

如果 5 个问题里有 2 个以上答不清，说明标题体系还不稳定。

## 10. 当前不建议做的事

现在先不建议：

- 为所有区块补非常复杂的中英文双命名系统
- 把所有运维区块强行改成用户化语言
- 在尚未确认哪些后台区会长期保留前，就先做重组件化抽象

当前更适合的是：

- 先让主链路标题语言完全稳定
- 再让验证和运维区块形成次级统一规则
- 最后再考虑更完整的 UI 文案系统

## 11. 当前结论

当前这套区块标题与阶段命名规范，可以概括成一句话：

**主链路说用户任务，判断区说机制逻辑，运维区说验证动作，同一阶段始终使用同一套命名骨架。**

这样后续再做 UI 优化时，改的就不只是“视觉”，而是整套产品表达的一致性。
