# 案例元数据驱动的关键复跑计划 v0.1

## 1. 本轮解决的问题

前面已经有了：

- 关键样例复跑计划
- 批量复跑脚本
- 复跑报告
- 差异报告

但关键复跑计划本身仍然是单独维护的静态清单。

这会带来一个问题：

- 你新增一个真实高频误判案例时
- 不仅要改案例文件
- 还要记得再改一份复跑清单

这不利于后续扩展。

所以这轮把“是否进入关键复跑计划”沉淀为案例自身的元数据。

## 2. 新增的案例元数据

### 2.1 `operations`

现在案例数据支持一个新的可选字段：

`operations`

其中包含：

- `keyCaseRerunPriority`
- `maintenanceTags`

### 2.2 含义

#### `keyCaseRerunPriority`

作用：

- 决定该案例是否进入关键复跑计划
- 同时决定在计划里的排序优先级

约定：

- `0` 表示不进入自动关键复跑计划
- `>0` 表示进入计划
- 数值越大，优先级越高

#### `maintenanceTags`

作用：

- 记录该案例为什么值得被纳入维护链路
- 后续可用于筛选：
  - `misclassified-seed`
  - `real-case`
  - `platform-bridge`
  - `high-priority-candidate`

## 3. 接入位置

### 3.1 案例校验层

文件：

- `src/domain/cases/validateCaseRecord.js`

新增：

- `normalizeOperations`

职责：

- 校验 `operations` 结构
- 补默认值

### 3.2 真实案例模板

文件：

- `src/domain/cases/buildRealCaseTemplate.js`

新增：

- 默认 `operations`

这样以后新建真实案例时，模板天然就给你预留了维护优先级入口。

### 3.3 案例列表输出

文件：

- `src/application/listAvailableCases.js`

新增输出：

- `keyCaseRerunPriority`
- `maintenanceTags`

这让前端或后续后台工具也能直接读到维护元数据。

## 4. 自动生成关键复跑计划

### 4.1 新增领域能力

文件：

- `src/domain/cases/buildKeyCaseRerunPlan.js`
- `src/domain/cases/buildGeneratedKeyCaseRerunPlanMarkdown.js`
- `src/domain/cases/buildObsidianGeneratedKeyCaseRerunPlanRecord.js`

职责：

- 从案例元数据里自动筛选出关键复跑样例
- 按优先级排序
- 生成结构化计划与 Markdown 计划说明

### 4.2 新增脚本

文件：

- `scripts/generate-key-case-rerun-plan.js`
- `scripts/export-obsidian-key-case-rerun-plan.js`

命令：

- `npm run generate:key-case-rerun-plan`
- `npm run export:obsidian-key-case-rerun-plan`

## 5. 当前运行方式

推荐顺序：

1. `npm run generate:key-case-rerun-plan`
2. `npm run rerun:key-cases`

现在 `rerun:key-cases` 默认优先读取：

- `data/operations/key-case-rerun-plan.generated.json`

如果该文件不存在，才会回退到：

- `data/operations/key-case-rerun-plan.json`

这样旧链路不会断，新链路也能逐步接管。

## 6. 当前效果

目前已通过案例元数据自动生成：

- `sample-001`
  - 优先级 `10`
- `real-001`
  - 优先级 `6`

计划排序因此自动变成：

1. `sample-001`
2. `real-001`

## 7. 为什么这一步重要

这一步看起来像是在加元数据，实际上是在把系统推向更可维护的方向：

- 案例决定自己在维护链中的角色
- 计划由数据生成，而不是人工重复维护
- 新增真实高频误判案例时，只需要改案例本身

这更接近真实产品的运作方式。

## 8. 下一步建议

### 8.1 增加更多维护标签约定

后续可以明确维护标签规范，例如：

- `misclassified-high-frequency`
- `rule-sensitive`
- `direction-sensitive`
- `real-user-priority`

### 8.2 做“按标签生成不同复跑计划”

例如：

- 方向规则专项复跑
- 反馈映射专项复跑
- 真实案例专项复跑

### 8.3 把真实高频误判案例逐步补进来

现在基础设施已经够用，下一步更重要的是把真实案例真正纳入这条链。
