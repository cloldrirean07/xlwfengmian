# 真实案例确认写入链路 v0.1

## 1. 这轮解决了什么问题

前一轮已经有：

- 真实案例录入表单
- 真实案例骨架预览

但那还只是“看一下会生成什么”，并不能真正把案例纳入代码侧真实案例体系。

所以这轮补上了：

- 真实案例确认写入链路

让前端入口从：

- `录入 -> 预览`

推进到：

- `录入 -> 预览 -> 确认写入`

## 2. 当前新增的代码分层

### 2.1 应用层

新增：

- `src/application/commitRealCaseScaffold.js`

职责：

- 读取当前真实案例 index
- 基于录入 payload 复用 `prepareRealCaseScaffold`
- 调用持久化层写入
- 写入后重置 case cache
- 返回前端可直接展示的结果

也就是把“正式写入”作为一个独立用例，而不是塞回脚本或页面层。

### 2.2 基础设施层

新增：

- `src/infrastructure/cases/resolveRealCaseStoragePaths.js`
- `src/infrastructure/cases/savePreparedRealCaseScaffold.js`

职责：

- 集中管理真实案例存储路径
- 负责把 `indexEntry` 与 `record` 真正落到：
  - `data/real-cases/index.json`
  - `data/real-cases/items/*.json`

同时保留：

- item 文件是否已存在的保护

避免重复写入覆盖。

### 2.3 服务层

新增接口：

- `POST /api/real-case-scaffold-commit`

位置：

- `src/server/server.js`

这样前端不需要直接理解文件系统，只通过 API 触发正式写入。

## 3. 当前前端如何接入

### 3.1 API 调用层

新增：

- `commitRealCaseScaffold`

位置：

- `public/app/api.js`

### 3.2 DOM 与状态

新增：

- `realCaseCommitResult`
- `latestRealCaseCommit`

位置：

- `public/app/dom.js`
- `public/app/state.js`

### 3.3 页面编排

在 `public/app/createApp.js` 新增：

- 未预览时阻止直接写入
- 点击确认写入后调用 commit API
- 成功后刷新预览结果和写入结果
- 成功后清空 `availableCases` 缓存

这让后续案例列表可以重新读取最新数据。

### 3.4 渲染层

位置：

- `public/app/renderers.js`

它负责展示：

- 写入文件路径
- 索引文件路径
- 写入时间
- 下一步建议

## 4. 当前为什么不直接接更多字段

这轮故意没有同时把：

- `contentTopic`
- `contentGoal`
- `assetDescription`
- `referencePreference`

等更完整内容字段塞进前端录入页。

原因是当前要先确认的是：

- 登记动作本身能否成立
- repo 侧真实案例数据链是否稳定
- 从页面写入代码侧数据是否可控

也就是说，这轮优先解决的是：

- “能不能写进去”

而不是：

- “一开始就把所有字段都写满”

## 5. 自动化验证范围

本轮新增自动化验证：

- `commitRealCaseScaffold writes index and item through injected storage`

验证方式不是直接污染正式案例库，而是：

- 用临时目录注入 `index.json`
- 注入 `items/`
- 验证写入后：
  - index 数量增加
  - item 文件生成
  - priority 等字段保留
  - cache reset hook 被触发

## 6. 当前价值

这轮之后，真实案例入口已经从“看得见”推进到“能落库”。

这意味着项目开始拥有一个真正的内部工作台雏形：

- 产品侧可以录入一条候选案例
- 系统可以给出骨架预览
- 确认后可以写入真实案例数据源

后续再往上补：

- 内容字段
- 回填工作单
- Obsidian 草稿联动

都会更顺。

## 7. UI 什么时候最适合正式优化

当前我的判断是：

**不要现在大改 UI。**

最合适的时机是下面这条最小主链完全稳定之后：

- `真实案例录入`
- `骨架预览`
- `确认写入`
- `真实案例维护链可重新读取`
- `至少 2~3 条真实案例能反复跑通`

原因很直接：

- 现在页面结构还会继续长
- 表单字段还会变
- 结果区还会增加更多状态
- 如果现在就做完整 UI 精修，很容易后面推翻布局

所以更合理的节奏是：

### 先做完产品主链

重点确认：

- 输入区最终有哪些字段
- 结果区最终要显示哪些块
- 真实案例维护链里哪些信息最重要

### 再和你一起讨论 UI 优化

那时候讨论会更有效，因为我们能围绕真实页面结构来决定：

- 信息层级
- 模块优先级
- 工作台视觉风格
- 移动端与桌面端差异

## 8. 建议的 UI 讨论节点

我建议把 UI 正式讨论放在以下节点之后：

### 节点 A

真实案例确认写入已经完成。

### 节点 B

前端可以重新读取到新增真实案例，并能继续进入维护链。

### 节点 C

你已经实际用 2~3 条案例试跑过这套页面，知道哪里最不顺。

到这个时候再讨论 UI，才不会只是“好不好看”，而会变成：

- 哪些区域最该强化
- 哪些操作最该缩短
- 哪些信息该前置或后置

这时做 UI 优化，产出质量会明显更高。
