# 真实批次试跑记录安全写回预览_v0.1

## 1. 目标

前一轮我们已经有：

- 人工复盘待补任务
- 人工复盘回流预览
- 真实批次试跑结论写回草稿

这次继续往前补一层：

- 真实批次试跑记录安全写回预览

它的作用不是直接覆盖真实批次试跑记录，而是先把：

- 当前真实记录原文
- 按人工复盘拟写回后的版本

放到同一份草稿里，供人工确认。

## 2. 为什么先做安全写回预览

现在已经走到比较接近正式写回的一步了。

如果这时直接覆盖真实批次试跑记录，风险主要有两类：

1. 人工判断还可能继续变化
2. 写回位置虽然清楚，但用户可能还想手改措辞

所以在真正“写回真实记录”之前，先增加一层安全预览，会更符合现在的验证节奏。

## 4. 当前预览如何处理真实记录

这次不是整篇重新生成真实批次试跑记录，而是按已知的关键行做安全替换：

- `这批案例最卡的环节`
- `哪个按钮或模块最该前置`
- `当前更像功能问题，还是界面问题`
- `这批试跑最关键的结论`
- `下一批还要不要继续同样赛道`
- `UI 优化是否已经到时机`

也就是说，这层预览更像“可控 patch”，而不是“整篇重写”。

## 5. 默认导出位置

Obsidian 默认目录：

- `05_验证与实验/批次试跑记录/人工复盘安全写回预览`

这样当前链路会继续分层：

- 人工复盘待补任务
- 人工复盘回流预览
- 真实批次试跑结论写回草稿
- 真实批次试跑记录安全写回预览
- 真实批次试跑记录

## 6. 对后续 UI 讨论的意义

这一步的价值仍然不是 UI 本身，而是让后续 UI 判断建立在：

- 已填写的人工判断
- 已对齐的写回草稿
- 已确认的真实记录写回预览

之上。

等这层也跑通后，再去谈正式写回和重跑 `UI readiness`，顺序会更稳。

## 7. 当前结论

可以把这次接入压缩成一句话：

**系统现在已经不只会生成写回草稿，还能在正式覆盖前给出一份真实批次试跑记录安全写回预览。**
