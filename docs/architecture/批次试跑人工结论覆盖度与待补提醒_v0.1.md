# 批次试跑人工结论覆盖度与待补提醒_v0.1

## 1. 本次补的是什么

在已有“人工结论回流”基础上，再补一层：

- 人工结论覆盖度统计
- 待补批次提醒
- 关键判断字段缺口提示

这样系统不只知道“有没有人写过结论”，还知道：

- 哪些关键人工判断已经开始稳定积累
- 哪些批次还没写
- 哪些批次虽然写了，但还缺最关键的判断字段

## 2. 为什么这一层重要

当前产品判断 UI 是否值得优化，不能只看：

- 自动摩擦点是否重复出现

还要看：

- 人工是否真的判断出“最卡环节”
- 人工是否能稳定说清“更像功能问题还是界面问题”
- 人工是否已经开始对“最该前置模块”形成共识
- 人工是否已经觉得“UI 优化到时机”

如果这些字段一直没人补，或者补得很散，那么现在讨论 UI，容易变成凭感觉。

## 3. 本次新增的关键统计

代码位置：
- `apps/web/src/domain/cases/buildBatchRunFrictionSummaryReport.js`
- `apps/web/src/domain/cases/buildBatchRunFrictionSummaryMarkdown.js`
- `apps/web/public/app/renderers.js`

新增统计包括：

- `missingManualReviewCount`
  - 完全未写人工结论的批次数
- `keyFieldCoverage`
  - 关键判断字段覆盖度
- `pendingBatchRows`
  - 待补人工判断的批次列表

## 4. 当前纳入覆盖度判断的关键字段

当前先只盯最影响 UI 决策的 4 个字段：

- `bottleneckStep`
  - 最卡环节
- `issueType`
  - 问题类型判断
- `prioritizedModule`
  - 最该前置模块
- `uiOptimizationTiming`
  - UI 时机判断

这是第一版最小集合，后续可以继续扩。

## 5. 前端现在会多显示什么

跨批次摩擦点汇总面板现在会额外显示：

- 已写人工结论批次
- 完全未写人工结论批次
- 人工判断覆盖度
- 建议优先补的批次

这样你在工作台里可以直接看到：

- 下一批不是先改界面
- 而是先补哪一批试跑结论
- 以及那一批具体缺的是哪类关键判断

## 6. 对产品推进的意义

这层补完后，产品推进顺序会更清楚：

1. 先跑真实批次
2. 再补人工结论
3. 看跨批次重复信号
4. 看人工关键字段是否开始收敛
5. 再决定是否进入 UI 优化讨论

## 7. 当前判断

按照当前架构，UI 优化不该作为当前主线。

更合理的时机是：

- 至少再多 1 到 2 批真实试跑
- 并且人工关键字段开始反复指向同一问题

在这之前，更应该优先提升：

- 试跑记录质量
- 人工复盘覆盖度
- 规则与建议输出的稳定性

## 8. 下一步建议

下一步最值得做的是：

1. 真实补一批现有试跑记录的人工结论
2. 再跑一批新内容
3. 观察待补提醒是否开始下降
4. 观察“最卡环节 / 问题类型 / 最该前置模块”是否出现重复

如果这三类字段开始重复，再正式进入 UI 优化讨论会更稳。
