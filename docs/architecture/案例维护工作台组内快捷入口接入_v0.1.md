# 案例维护工作台组内快捷入口接入_v0.1

## 1. 本轮为什么继续往前推

前面已经完成：

- 案例维护工作台双层分组
- 单条录入流与批量维护流的结构边界

但二级结构清楚，不等于用户就能快速到达。

当前如果用户进入案例维护工作台，虽然已经能看懂：

- 有单条录入层
- 有批量维护层

但仍然要靠滚动去找。

所以这轮补的不是正式导航系统，而是更轻的一步：

- 组内快捷入口

## 2. 本轮要解决的问题

如果没有组内快捷入口，会出现两个小但真实的摩擦点：

1. 用户知道自己该去哪层，但还要滚动定位
2. 首页已经开始变长，组内层级一多，来回跳转成本会提高

所以这轮的目标是：

- 在不引入复杂导航的前提下
- 让案例维护组先具备最小的组内跳转能力

## 3. 本轮实际改动

## 3.1 在案例维护组头部新增快捷入口

在案例维护工作台的 `group-intro` 中新增：

- `group-shortcut-row`

当前包含两个入口：

- `先看单条录入`
- `直接去批量维护`

## 3.2 为两段二级结构补锚点

新增：

- `id="single-case-flow"`
- `id="batch-maintenance-flow"`

这样快捷入口不需要依赖额外脚本，就能直接跳到对应层级。

## 3.3 为什么只先补两个入口

当前只补这两个，是因为它们已经覆盖了案例维护组里最关键的分流判断：

- 我现在是先跑通一条
- 还是直接进入批量维护

其他内容如：

- 案例概览
- 平台复核

暂时仍然收在“批量维护流”这一层里，不急着过早拆得太细。

## 4. 样式实现方式

样式层新增：

- `group-shortcut-row`

以及组内链接样式。

设计目标是：

- 视觉上接近轻导航
- 但层级明显低于首页主导航
- 在移动端下自动整行展示，便于点击

## 5. 涉及文件

- `apps/web/public/index.html`
- `apps/web/public/styles.css`

本轮没有修改：

- `createApp.js`
- `dom.js`
- 业务逻辑与数据结构

## 6. 这轮的产品意义

这轮的意义不在于多了两个链接，而在于它是一次非常有价值的“轻导航预演”。

它帮助我们验证一件事：

- 案例维护工作台已经开始值得有自己的组内导航能力

如果这一步成立，后续再讨论：

- 首页轻导航
- `/cases` 页内导航
- tabs 或二级导航

都会更自然。

这已经比单纯讨论“页面长不长”更接近真实产品优化。

3. 之后再进入更系统的 UI 优化讨论
