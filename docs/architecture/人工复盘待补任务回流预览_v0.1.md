# 人工复盘待补任务回流预览_v0.1

## 1. 目标

前面我们已经完成了三步：

1. 发现待补人工复盘批次
2. 导出人工复盘待补任务草稿
3. 识别这份草稿是否已经被填写

这次要继续补的是：

- 把已填写草稿整理成“可回流的批次试跑结论预览”

也就是说，系统先不要直接改真实批次试跑记录，而是先明确：

- 如果现在要回流，会写回哪些关键字段

## 2. 为什么先做预览而不是直接写回

这里故意先做“预览”，而不是直接覆盖原记录，有两个原因：

1. 当前还在验证人工复盘字段是否真的足够稳定
2. 先预览可以让你确认回流逻辑有没有偏

所以这一步的定位是：

- 回流前的确认层

## 3. 当前新增产物

领域层：

- `buildBatchReviewManualTaskBackfillPreview.js`

应用层：

- `runBatchReviewManualTaskCardPreview.js` 中新增 `backfillPreview`

## 4. 当前预览会输出什么

系统现在会整理出：

- 当前状态
- 目标批次
- 已填写字段
- 仍缺字段
- 可回流的 4 项关键人工判断 patch

这 4 项是：

- `bottleneckStep`
- `issueType`
- `prioritizedModule`
- `uiOptimizationTiming`

## 5. 当前状态定义

### 5.1 `no-task-card`

- 还没有待补任务草稿

### 5.2 `no-manual-input`

- 草稿已经导出，但还没有填写关键人工判断

### 5.3 `partial-ready`

- 已经填写了一部分，可以开始预览回流
- 但还没达到完整回流条件

### 5.4 `ready-to-backfill`

- 4 个关键字段都已填写
- 可以作为真实批次试跑结论回流预览输入

## 6. 这对后续 UI 讨论的价值

这一步很关键，因为它让“补完人工复盘后重跑 UI 判断”开始有了更明确的中间层。

后续顺序会更清楚：

1. 导出任务草稿
2. 填写任务草稿
3. 看回流预览
4. 再决定是否正式写回并重跑 UI readiness

## 7. 当前结论

可以把这一步压缩成一句话：

**系统现在不只知道任务草稿有没有被填写，也开始能把这些填写内容整理成可回流的批次试跑结论预览。**
