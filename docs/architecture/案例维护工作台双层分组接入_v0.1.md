# 案例维护工作台双层分组接入_v0.1

## 1. 本轮为什么开始收这层

前面已经完成：

- 首页三组分层
- 三组默认显隐策略
- 三组使用场景微说明

但案例维护工作台内部仍然有一个结构问题：

- 单条录入
- 批量维护
- 案例概览
- 平台复核

这些能力虽然都属于“案例维护”，但它们不是同一类动作。

如果继续平铺在一个组里，用户虽然知道它们都属于案例维护，但仍然需要自己判断：

- 我现在是在做“先录一条”
- 还是在做“已经积累起来后的批量维护”

所以这轮开始收的，是案例维护工作台内部的第二层边界。

## 2. 本轮要解决的问题

案例维护组当前最明显的问题不是内容太多，而是缺少中间层。

原先页面结构里：

- 单条录入预览台
- 单条骨架确认
- 批量录入
- 批量写入预览
- 案例已写入概览
- 平台案例复核台

会连续往下排。

这会带来两个问题：

1. 用户不容易判断“我该从单条还是批量开始”
2. 批量维护与复核能力会显得像只是录入页的继续，而不是另一种工作模式

所以这轮补的是“组内二级分层”，不是新的页面功能。

## 3. 当前二级结构判断

本轮把案例维护工作台内部拆成两层：

### 3.1 单条录入与确认写入

包含：

- `真实案例录入预览台`
- `真实案例骨架预览`

这层的职责是：

- 先让一条案例从录入到确认写入跑通
- 用最小链路验证字段结构和写入逻辑

### 3.2 批量维护、回填与复核

包含：

- `批量真实案例录入`
- `批量写入预览`
- `真实案例已写入概览`
- `平台案例复核台`

这层的职责是：

- 当案例开始积累后，进入更高频的维护模式
- 承载批量回填、试跑记录、案例库浏览与平台复核

## 4. 本轮实际改动

## 4.1 新增两段 `subgroup-intro`

在案例维护工作台内部新增两段中间说明：

- `Single Case Flow`
- `Batch Maintenance Flow`

它们各自包含：

- `section-kicker`
- 二级标题
- 一段说明

作用是：

- 给同一组里的不同工作模式加一层中间边界

## 4.2 当前二级标题口径

当前页面使用：

- `单条录入与确认写入`
- `批量维护、回填与复核`

这两个标题的设计目标是：

- 第一层强调“先跑通一条”
- 第二层强调“进入持续维护阶段”

这样用户不需要看完整个组，先看二级标题就能判断当前该去哪部分。

## 4.3 样式层新增 `subgroup-intro`

在样式层新增：

- `subgroup-intro`

它采用比主组头更轻的视觉层级：

- 轻背景
- 轻边框
- 中等字号

目的是：

- 让它成为组内层级提示
- 但不要抢过案例维护组本身的组头

## 5. 涉及文件

- `apps/web/public/index.html`
- `apps/web/public/styles.css`

本轮没有改：

- `createApp.js`
- `dom.js`
- 任何案例维护 API 或应用层逻辑

## 6. 为什么这一步很重要

这一步的价值不在于页面更长，而在于它开始表达：

- 案例维护不是一坨功能
- 而是至少有“单条验证模式”和“批量维护模式”两种使用阶段

这对后续拆 `/cases` 页面很关键，因为以后真正拆页时，很可能也要沿着这两层去组织页面结构。

## 9. 对后续 UI 优化的意义

这一步做完后，后续 UI 优化就可以进入更像产品结构优化的阶段：

- 判断案例维护组是否要加组内锚点
- 判断是否要把单条与批量做成 tabs 或二级导航
- 再决定何时正式拆页

也就是说，现在离真正有资格讨论更系统的案例页 UI，已经更近了一步。
