# 人工复盘补齐后的UI再判断链路_v0.1

## 1. 目标

这份文档要解决的不是“人工复盘重不重要”，而是把下面这条动作正式固定下来：

- 先补人工复盘关键字段
- 再重跑跨批次摩擦点汇总
- 再重跑 UI readiness
- 最后才决定是否进入首页系统 UI 讨论

之前项目里已经有：

- `UI readiness` 报告
- `跨批次摩擦点汇总`
- `批次复盘看板`

但还缺一层更直接的动作承接：

- 当我们知道“还差人工复盘”之后，系统应该明确告诉你下一步怎么做

所以这次补的是一条“再判断链路”，而不是新加一个判断面板。

## 2. 为什么这一步现在必须补

当前首页系统 UI 时机已经被判断为：

- `near-ready`

这说明项目已经不是“完全不该谈 UI”。

但当前最关键的缺口也已经很明确：

- 人工复盘关键字段还不完整

如果系统只告诉你“还差人工复盘”，却不把补完后的下一步动作固定下来，后续很容易出现两类问题：

1. 补了字段，但没人回头重跑判断
2. 一边补字段，一边又提前开 UI 方案，顺序重新变乱

所以这一步的本质，是把“差一点点就能讨论 UI”的状态，变成一条可以重复执行的产品推进路径。

## 3. 这条链路要接在哪里

当前最合适的接入位置不是首页主链路，也不是新开一个独立工作台。

最合适的位置是：

- `批次复盘看板`

原因：

1. 这块本来就负责汇总当前复盘覆盖状态
2. 这块已经同时看 `UI readiness`、跨批次信号和人工复盘趋势
3. 这里天然就是“接下来先做什么”的决策台

所以这次的设计原则是：

- 不新增孤立模块
- 直接把“再判断链路”挂到现有复盘看板里

## 4. 当前链路状态定义

代码侧新增一个固定结构：

- `uiRecheckPlan`

当前分成 3 种状态。

### 4.1 `awaiting-manual-fill`

含义：

- 还有优先批次没补完人工复盘字段

这时系统应该提示：

1. 先补哪一批
2. 缺哪些关键字段
3. 这批当前最强摩擦点是什么
4. 补完后要先重跑什么

### 4.2 `grow-more-evidence`

含义：

- 当前没有明确优先批次，但整体证据还不够稳定

这时系统应该提示：

1. 继续补真实样本
2. 让至少 1 批人工关键字段补完整
3. 再统一重跑摩擦点汇总、UI readiness 和复盘看板

### 4.3 `ready-for-ui`

含义：

- `UI readiness` 已经达标
- 人工复盘趋势也已经稳定

这时系统应该提示：

1. 可以进入首页系统 UI 讨论
2. 先围绕首页主链路讨论
3. 不先扩散到整站统一美化

## 6. 前端现在会多展示什么

批次复盘看板现在除了原有的：

- 当前汇总
- 当前判断
- 当前最该补的批次
- 下一步动作
- 复盘后操作清单

还会新增一块：

- `人工复盘补齐后的再判断链路`

这块会显示：

- 当前状态
- 当前阻塞
- 建议顺序

它的作用不是替代原有 checklist，而是把“补完人工复盘之后，系统判断应该怎么连续推进”说得更明确。

## 7. 这对后续 UI 讨论的价值

这一步很重要，因为它把 UI 时机判断从一句建议，推进成了一条重复可执行的流程。

后续你再看项目，不会只是看到：

- 还差人工复盘

而会看到：

1. 先补哪一批
2. 补完后先重跑什么
3. 什么时候才真的进入 UI 讨论

这能明显降低后续推进中的顺序混乱。

## 8. 当前结论

可以把这次接入压缩成一句话：

**项目现在不只是知道“还没到 UI 讨论时点”，而是已经开始把“补齐人工复盘后如何重新判断”做成系统内固定动作。**
