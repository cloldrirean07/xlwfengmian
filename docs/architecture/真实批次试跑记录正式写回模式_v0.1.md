# 真实批次试跑记录正式写回模式_v0.1

## 1. 目标

前一轮我们已经有：

- 真实批次试跑记录安全写回预览
- 正式写回确认读回与就绪判断

这次继续补最后一层：

- 真实批次试跑记录正式写回执行

它的目标不是重新生成一篇新文档，而是在人工确认通过后，把安全写回预览里的“写回后预览”正式覆盖回目标记录。

## 2. 当前新增产物

领域层：

- `parseBatchReviewManualSafeWritePreviewNote.js`
- `buildBatchReviewManualSafeWritePreviewMarkdown.js`

应用层：

- `exportBatchReviewManualFormalWriteToObsidian.js`

服务端接口：

- `POST /api/batch-review-manual-formal-write-export`

前端接线：

- `apps/web/public/app/api.js`
- `apps/web/public/app/createApp.js`
- `apps/web/public/app/renderers.js`

## 3. 正式写回的执行规则

正式写回当前严格走 gate：

1. 先读取最近一份安全写回预览
2. 再读取其中的人工确认字段
3. 只有同时满足下面两个条件，才允许继续：
   - `是否已经可以进入正式写回` 为明确肯定
   - `哪几行仍需手改` 为空

如果不满足，就直接中止，不覆盖真实批次试跑记录。

## 4. 当前正式写回的数据来源

正式写回不再重新根据任务卡或回填草稿现算一版内容，而是以安全写回预览文档为准。

具体来说，系统会从预览文档中解析：

- `目标记录`
- `写回后预览`

然后把 `写回后预览` 作为最终正式写回内容覆盖到目标记录。

这样可以保留你在安全预览阶段已经做过的人工调整，不会被代码侧再次重算覆盖掉。

## 5. 当前增加的保护措施

这次正式写回额外保留了几层保护：

- 写回前先读目标记录原文
- 在 `outputs/batch-review-manual-formal-write/` 下保留写回前备份
- 在同目录下保留本次正式写回正文和状态 json
- 在 `outputs/obsidian-export-logs/batch-review-manual-formal-write/` 下记录读回结果

也就是说，正式写回虽然会覆盖目标记录，但不是“无痕覆盖”。

## 6. 为什么这一步比 UI 优化更优先

现在我们正在补的是“人工复盘结果如何稳定回到真实记录”。

如果这条链路还没闭环，就提前进入 UI 优化，会出现两个问题：

1. 真实验证结论还没稳定沉淀
2. UI 讨论会重新滑回主观感觉，而不是基于真实记录

所以当前顺序仍然合理：

- 先补真实复盘链路
- 再稳定正式写回
- 再决定什么时候进入 UI 优化

## 7. 当前结论

可以把这次接入压缩成一句话：

**系统现在已经能在人工确认通过后，把安全写回预览中的最终版本正式覆盖回真实批次试跑记录。**
