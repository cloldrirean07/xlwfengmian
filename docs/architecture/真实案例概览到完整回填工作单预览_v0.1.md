# 真实案例概览到完整回填工作单预览 v0.1

## 1. 这轮新增了什么

上一轮已经能从真实案例概览中看到：

- 这条案例先补什么

这轮进一步把它推进成：

- 这条案例的完整回填工作单预览

也就是说，现在不只是给“前三项提示”，而是已经能把整条案例的回填任务清单直接展示到前端。

## 2. 当前代码结构怎么接

### 2.1 应用层

在：

- `src/application/runRealCaseFillPreview.js`

中补充：

- `buildRealCaseFillSheetMarkdown(fillSheet)`

让单条真实案例回填预览返回：

- `fillSheet`
- `fillSheetMarkdown`

而不是只返回结构化任务项。

### 2.2 前端概览卡片动作

在真实案例概览中新增：

- `查看完整回填工作单`

这个动作和“查看这条先补什么”共用同一条回填预览链路，但前端会把完整 markdown 工作单也展示出来。

### 2.3 前端维护预览区

在：

- `renderRealCaseMaintenancePreview`

中新增：

- `完整回填工作单预览`

当前展示内容包括：

- 当前就绪度
- 已完成检查数
- 缺失字段数
- 当前最该先补的字段
- 完整 markdown 工作单

## 3. 这一步的价值

这轮之后，真实案例概览不只是在做“摘要提示”，而是已经开始承接：

- 单条真实案例的完整维护动作预览

这很重要，因为它让你后面开始真正试用时，可以直接判断：

- 这条案例还差什么
- 任务顺序合不合理
- markdown 工作单的结构是否好用

## 4. 当前主链路状态

到这里，真实案例相关路径已经非常接近一个内部工作台的最小主链：

- 录入
- 预览
- 写入
- 重读概览
- 同步预览
- 回填优先项预览
- 完整回填工作单预览

这已经足以支撑后续继续补真实案例，而不是只停在“技术演示”。

## 5. UI 为什么还不适合现在大改

这轮再次说明，当前还不适合正式做大规模 UI 优化。

原因不是 UI 不重要，而是维护链区块还在继续生长：

- 同步预览
- 优先项预览
- 完整工作单预览

这些模块之间最终怎么排布，要等你真的拿 2~3 条案例跑一轮之后才会更清楚。

所以更合理的节奏依然是：

1. 继续跑通真实案例主链
2. 让页面结构基本稳定
3. 再专门讨论 UI 优化

## 6. 下一步最顺的方向

下一步最自然的是：

- 把完整回填工作单和 Obsidian 草稿/导出链再接近一点

或者：

- 从真实案例概览继续进入优先级看板

这两步做完后，再讨论 UI，会更准。
