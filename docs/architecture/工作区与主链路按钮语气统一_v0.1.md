# 工作区与主链路按钮语气统一_v0.1

## 1. 这轮为什么继续做 UI

在已经完成：

- 第一轮到第二轮按钮层级与动作语气统一

之后，主链路里的 CTA 已经开始形成统一节奏。

但页面上还有一段非常关键的按钮系统没有完全收进来：

- 工作区建议生成按钮
- 工作区采纳按钮
- 工作区不采纳按钮
- 工作区决策后的状态说明

如果主链路的按钮都已经在说：

- 进入下一步
- 填写反馈
- 生成结果

而工作区仍然在说：

- 工作区建议
- 采纳这次建议
- 不采纳这次建议

那用户仍然会感受到：

- 主链路是一套语言
- 工作区又是一套语言

所以这轮的目标，是把工作区也纳入同一套动作语气。

## 2. 这轮要解决的问题

本轮主要解决两个问题：

1. 工作区按钮是否明确表达“这是当前这一步的动作”
2. 工作区与主链路按钮是否能说同一种推进语言

重点不在于按钮多不多，而在于它们是否统一回答：

- 现在在做哪一步
- 做完会不会进入下一步

## 3. 设计原则

本轮依旧只做轻量统一：

- 不改工作区逻辑
- 不改工作区数据结构
- 不改工作区生成链路

只统一动作口径。

统一原则是：

- 生成类动作强调“这一步”
- 采纳类动作强调“继续下一步”
- 拒绝类动作强调“这一步先不采纳”

这样工作区会更像主链路中的一个阶段，而不是旁支模块。

## 4. 本轮具体改动

## 4.1 工作区生成按钮改成阶段动作语言

在 `index.html` 中，原来的：

- `生成工作区建议`

调整为：

- `生成这一步建议`

这次改动的意义在于：

- 把“工作区”这个模块名退后
- 把“当前正在处理哪一步”放到前面

这样用户更容易把它理解为主链路的一环，而不是一个额外工具。

## 4.2 工作区采纳按钮改成推进动作

原来的：

- `采纳这次工作区建议`

调整为：

- `采纳并继续下一步`

这样按钮表达的重点就从：

- 你是否接受这个模块产出的建议

变成：

- 你是否决定带着这一步的结论继续往下走

这和主链路中“进入第二轮”“生成结果”的逻辑更一致。

## 4.3 工作区拒绝按钮改成阶段性拒绝

原来的：

- `这次建议不采纳`

调整为：

- `这一步先不采纳`

这里的变化很重要：

- 它不再像一个绝对否定
- 而更像一个阶段性判断

这更符合真实产品语境：

- 不是说这个系统永远不行
- 而是这一步先不带入后续链路

## 4.4 工作区决策状态文案同步收口

在 `renderWorkspaceDecisionStatus` 中，对决策后的说明也做了同一方向的统一：

### 采纳时

强调：

- `这一步建议已采纳`
- 现在回到下方方向卡继续下一步

### 不采纳时

强调：

- `这一步建议不会带入第二轮`
- 如有需要，可以重新生成这一步建议

这样按钮文字和状态文字会说同一套话，而不是按钮一种说法、状态又另一种说法。

## 5. 涉及文件

- `apps/web/public/index.html`
- `apps/web/public/app/renderers.js`

## 7. 这轮带来的价值

这一轮之后，工作区不再像一个话术独立的旁支模块，而开始与主链路使用同一套推进语言。

最直接的提升是：

- 用户更容易理解工作区也是主链路的一部分
- 采纳 / 不采纳不再只是功能判断，而更像流程判断
- 页面整体动作语气更稳定

## 8. 对后续 UI 的意义

到这一步，当前项目的 CTA 体系已经从：

- 单点按钮优化

进一步进入：

- 跨阶段的动作语言统一

所以下一步如果继续推进，更值得看的将是：

1. 是否要整理一版完整的按钮层级规范
2. 是否需要把主按钮 / 次按钮 / 阶段性按钮的使用场景写成规则
3. 等真实案例再多一些后，再进入更完整的系统级视觉统一
