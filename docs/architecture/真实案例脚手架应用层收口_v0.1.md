# 真实案例脚手架应用层收口 v0.1

## 1. 本轮解决的问题

前面虽然已经有：

- `scaffold-real-case.js`
- `scaffold-real-cases-batch.js`

但它们的业务逻辑还主要留在脚本里。

这会带来两个问题：

- 后续如果网页端、管理后台、接口层也要新增真实案例，就会重复写一遍逻辑。
- 脚本越写越厚，测试也只能绕着命令行走，不利于长期维护。

所以这轮把“真实案例脚手架”的核心逻辑正式收回 `application` 层。

## 2. 本轮新增的应用层能力

### 2.1 单条真实案例脚手架

新增：

- `src/application/prepareRealCaseScaffold.js`

职责：

- 校验当前 `real-case index` 是否可用
- 检查 `id` 是否重复
- 统一生成默认 `obsidianCasePath`
- 产出结构化的：
  - `record`
  - `indexEntry`
  - `fileName`

这样脚本层不再自己拼业务字段。

### 2.2 批量真实案例脚手架

新增：

- `src/application/prepareRealCaseBatchScaffold.js`

职责：

- 批量读取待新增项
- 逐条复用 `prepareRealCaseScaffold`
- 生成：
  - `created`
  - `nextIndex`

这样批量逻辑不再单独维护另一套模板拼装规则。

## 3. 当前分层变化

### 3.1 调整前

- `scripts`
  - 既负责命令行输入解析
  - 又负责真实案例业务拼装
  - 还负责 index 生成规则

### 3.2 调整后

- `scripts`
  - 只负责：
    - 读参数
    - 读文件
    - 调用应用层
    - 写结果
- `src/application`
  - 负责：
    - 单条脚手架准备
    - 批量脚手架准备
- `src/domain`
  - 继续负责：
    - `buildRealCaseTemplate`
    - 真实案例结构本体

也就是现在形成：

`script -> application -> domain`

这条链路。

## 4. 本轮同时修正的细节

### 4.1 批量脚本路径解析

`scaffold-real-cases-batch.js` 中原本对 `__dirname` 的处理不够规范。

这轮统一改为：

- `fileURLToPath`
- `dirname`

让脚本路径解析与项目里其他脚本保持一致。

### 4.2 dry-run 输出保持稳定

这轮确保重构后 dry-run 仍然能稳定输出：

- `indexEntry`
- `record`
- `operations`

避免只是“内部重构成功”，但外部命令输出格式悄悄变了。

## 5. 新增测试覆盖

本轮新增两条测试：

- `prepareRealCaseScaffold returns record and index entry with default obsidian path`
- `prepareRealCaseBatchScaffold creates multiple index-ready items`

后续又补了两条预览能力测试：

- `createRealCaseScaffoldPreview uses current index and returns preview payload`
- `createRealCaseBatchScaffoldPreview returns preview-ready batch payload`

验证重点：

- 默认 `obsidianCasePath` 是否正确生成
- `status` 是否保留
- `keyCaseRerunPriority` 是否传递
- `maintenanceTags` 是否传递
- 批量场景下是否能顺序生成多条待写入对象

## 6. 向真实产品入口多推进了一步

为了让这套能力不只停留在命令行，本轮又新增了最小 API 预览入口：

- `src/infrastructure/cases/loadRealCaseIndex.js`
- `src/application/createRealCaseScaffoldPreview.js`
- `src/application/createRealCaseBatchScaffoldPreview.js`

并在 `src/server/server.js` 挂出：

- `POST /api/real-case-scaffold-preview`
- `POST /api/real-case-batch-scaffold-preview`

这两个接口当前只做“预览”，不直接落库。

这样后面做网页录入页、内部管理台、或更轻量的真实案例录入面板时，都可以先调用同一套预览能力，再决定是否写入。

## 7. 为什么这一步重要

这不是单纯为了代码好看，而是为了后面的真实产品推进。

后续你大概率会继续增加：

- 更多真实案例
- 半自动导入入口
- 后台人工录入入口
- 平台案例转真实案例入口

如果脚手架逻辑只活在脚本里，这些入口都会各写各的。

现在先把“新增真实案例”的最小公共逻辑固定在 `application`，后面无论从哪里触发，都可以复用同一条链路。

## 8. 当前结论

这轮之后，真实案例脚手架相关能力的职责边界更清楚了：

- 模板结构在 `domain`
- 新增流程编排在 `application`
- 文件读写和命令入口留在 `scripts`

这更符合后续继续拆出：

- `apps/admin`
- `apps/api`
- 更完整的真实案例维护工作台

的长期方向。
