# 关键样例复跑机制 v0.1

## 1. 为什么需要这层机制

这个项目的核心不是单次生成，而是：

- 规则会持续变
- 误判会持续出现
- 案例会持续补
- 修订任务会持续回流

只要规则层升级，旧样例导出就可能变成历史快照。

如果没有一条固定复跑机制，就会出现：

- 前端看到的是新规则
- `case-runs/result.json` 还是旧快照
- 误判样本导出和任务单混杂旧数据

所以这轮新增的，不只是一个脚本，而是一条“规则升级后的标准维护流程”。

## 2. 本轮新增内容

### 2.1 关键样例复跑计划

文件：

`apps/web/data/operations/key-case-rerun-plan.json`

职责：

- 定义规则升级后优先复跑的关键样例 ID
- 定义需要顺手刷新的下游报告目标

当前默认清单：

- `sample-001`
- `real-001`

后续你可以继续往这里加，不需要改脚本主体。

### 2.2 批量复跑脚本

文件：

`apps/web/scripts/rerun-key-cases.js`

职责：

1. 读取关键样例复跑计划
2. 依次复跑每个 case
3. 刷新 `outputs/case-runs/<caseId>/result.json` 与 `summary.md`
4. 重新生成：
   - `reviewed-misclassified`
   - `rule-revision-task-sheet`
5. 生成本轮关键样例复跑报告

### 2.3 复跑报告

文件：

- `src/domain/cases/buildKeyCaseRerunReport.js`
- `src/domain/cases/buildKeyCaseRerunMarkdown.js`
- `src/domain/cases/buildObsidianKeyCaseRerunRecord.js`

输出内容包括：

- 本轮复跑计划
- 实际复跑的 case
- 每个 case 的首轮主方向
- 首轮命中信号
- 二轮选中方向
- 当前负向映射
- 下游误判样本与规则任务单刷新结果

## 3. 命令入口

新增命令：

- `npm run rerun:key-cases`
- `npm run export:obsidian-key-case-rerun`

### `rerun:key-cases`

作用：

- 一次性完成关键样例复跑与下游报告刷新

### `export:obsidian-key-case-rerun`

作用：

- 将复跑报告同步到 Obsidian

## 4. 为什么这样设计

### 4.1 清单可改

关键样例不是写死在脚本里的，而是放在 `data/operations` 下。

这样后续：

- 你新增真实案例
- 你新增误判重点样例
- 你想区分不同复跑计划

都可以在数据层扩，不需要重写脚本。

### 4.2 脚本负责“动作链”

复跑脚本本身负责：

- 跑 case
- 刷新报告
- 留下汇总记录

这样比手动依次执行多个命令更稳，也更接近真实产品维护方式。

### 4.3 报告负责“可追踪”

每次规则升级后，如果都生成一份复跑报告，你后面回看时就能知道：

- 这轮规则升级影响了哪些关键样例
- 哪些方向判断变了
- 哪些误判样本和任务单被刷新了
