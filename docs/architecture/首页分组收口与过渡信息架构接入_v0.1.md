# 首页分组收口与过渡信息架构接入_v0.1

## 1. 本轮为什么开始动代码

在前面已经完成：

- 按钮层级与动作语气规范
- 区块标题与阶段命名规范
- 首页页面分层与拆页建议

之后，继续只停留在文档层已经不够了。

当前首页的真实问题不是“功能不够”，而是：

- 主链路
- 案例维护链
- 验证与复盘链

都已经存在，但缺少清晰边界。

所以这一轮开始做的不是正式拆页，而是先把首页做成更合理的“过渡信息架构”。

## 2. 这轮改动目标

本轮要解决的是：

1. 让首页主链路之外的能力不再像同级主内容一样平铺
2. 让案例维护与验证复盘具备明确分组边界
3. 为后续 `/cases`、`/validation` 拆页预留稳定结构

也就是说，这轮是在做：

- 信息架构收口

不是在做：

- 全站视觉重构
- 真正的多页面拆分

## 3. 本轮实际改动

## 3.1 新增三类首页分组容器

在 `apps/web/public/index.html` 中新增：

- `workspace-group workspace-group-tools`
- `workspace-group workspace-group-cases`
- `workspace-group workspace-group-validation`

作用分别是：

- `tools`
  - 放主链路辅助验证工具
- `cases`
  - 放真实案例维护链
- `validation`
  - 放 UI 时机判断与批次复盘链

这样首页开始从“很多面板顺着往下排”，变成“几组职责不同的面板分层排列”。

## 3.2 新增每组的说明头部

每个分组前都新增：

- `group-intro`

它承担的不是装饰，而是明确说明：

- 这一组是干什么的
- 它是否属于主链路
- 为什么会暂时留在首页

三组当前标题分别是：

- `主链路辅助验证工具`
- `案例维护工作台`
- `验证与复盘工作台`

## 3.3 保留首页锚点，但把锚点挂到分组上

为了不打断现有跳转逻辑：

- `#real-case-form`
- `#ui-readiness-section`
- `#review-dashboard-section`

仍然保留，但现在优先定位到对应分组或分组内部关键面板，而不是更零散的表单节点。

这让首页跳转语义更接近“跳到某一类工作区”。

## 3.4 真实案例录入表单单独改名

原本案例录入表单本身使用：

- `id="real-case-form"`

这会和新的案例分组锚点冲突。

所以本轮改为：

- `id="real-case-intake-form"`

这样：

- 跳转锚点仍然可以稳定指向案例维护组
- 表单本身保留明确的录入语义

## 3.5 新增分组层样式

在 `apps/web/public/styles.css` 中新增：

- `workspace-group`
- `group-intro`
- `workspace-group-tools .group-intro`
- `workspace-group-cases .group-intro`
- `workspace-group-validation .group-intro`

这不是在建立完整设计系统，而是用最小样式成本先拉开层次：

- 工具组偏辅助色
- 案例组偏暖色维护感
- 验证组偏冷静复盘感

## 4. 这轮没有做什么

这轮刻意没有做：

- 正式拆路由
- 改 API 结构
- 改应用层逻辑
- 改任何分析、案例、复盘数据结构

原因是当前更重要的是：

- 先把首页的职责边界说清楚
- 再决定哪些真的值得拆页

## 5. 涉及文件

- `apps/web/public/index.html`
- `apps/web/public/styles.css`

本轮没有修改：

- `public/app/createApp.js`
- `public/app/renderers.js`
- `src/application/*`
- `src/domain/*`

## 7. 这轮带来的价值

这轮之后，首页虽然仍然是总览工作台，但已经不再是“所有东西连续堆叠”的状态。

最直接的价值是：

- 主链路以外的能力开始被正确降级和归组
- 首页更接近真实产品的过渡状态
- 后续拆 `/cases` 与 `/validation` 时，不需要重新发明页面边界

## 8. 对后续 UI 优化的意义

这轮之后，下一步 UI 优化终于可以更聚焦：

1. 先优化主链路本身
2. 再优化首页分组之间的视觉区隔
3. 最后等拆页后，再分别优化案例页和复盘页

这比直接对整个长首页一起做“美化”更稳。

## 9. 下一步建议

下一步最值得继续推进的是：

1. 给首页三组增加更轻的组内导航或折叠策略
2. 判断 `Prompt / 样例` 是否要默认折叠
3. 视情况开始把案例维护链收口成 `/cases` 的路由草案
