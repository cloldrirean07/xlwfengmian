# 批次试跑最近人工结论覆盖状态_v0.1

## 1. 本次补的是什么

在“批次试跑记录预览”里，新增最近一次人工结论覆盖状态读取能力。

也就是说，现在系统不只会：

- 生成本次批次试跑记录
- 提示你这次该先填哪些人工结论

还会额外告诉你：

- 这批上一次有没有真正写人工结论
- 上一次已经填了哪些关键字段
- 上一次还缺哪些关键字段

## 2. 为什么这层重要

如果没有这层状态，用户虽然能看到“这次该填什么”，但并不知道：

- 这批是不是早就写过
- 是完全没写，还是只写了一半
- 这次到底应该补旧缺口，还是重新完整复盘

所以这层的价值不是“新增更多内容”，而是让批次复盘形成连续性。

## 3. 当前实现方式

本次新增：

- 共享关键字段定义
  - `apps/web/src/domain/cases/batchRunManualReviewKeyFields.js`
- 最近人工结论状态读取
  - `apps/web/src/application/loadLatestRealCaseBatchRunManualReviewStatus.js`

它会基于：

1. 现有批次试跑记录导出日志
2. 定位最近一次导出的 Obsidian 笔记
3. 读取笔记中的人工结论字段
4. 判断关键字段覆盖情况

## 4. 当前会读哪些状态

当前输出包括：

- 最近导出时间
- 导出动作
- 是否已有人工结论
- 已填写字段数
- 已填写关键字段
- 仍缺的关键字段

这里的“关键字段”仍然沿用统一的 4 项：

- 最卡环节
- 问题类型判断
- 最该前置模块
- UI 时机判断

领域层：

前端渲染：

## 6. 当前前端会多显示什么

批次试跑记录预览现在会多一个区块：

- 最近一次人工结论覆盖状态

这个区块会直接显示：

- 最近导出
- 当前覆盖
- 已填关键字段
- 还缺关键字段

所以它更像一个“上一轮复盘接力面板”，而不是只看当前预览。

## 7. 为什么这层对 UI 判断有帮助

后续是否进入 UI 优化讨论，不只是看：

- 当前这一批卡在哪

还要看：

- 同一批次是不是反复没补完整
- 哪些关键判断总是缺失
- 人工字段是否开始稳定积累

这层状态让我们更容易判断：

- 是用户不愿意复盘
- 还是产品没有让复盘足够顺手

这本身就是 UI 与流程判断的重要信号。

## 8. 当前判断

现在产品已经开始具备：

- 当前试跑指引
- 历史复盘覆盖状态
- 跨批次汇总读取能力

这说明离“有证据地讨论 UI”更近了一步，但仍建议先继续跑真实批次。

## 9. 下一步建议

下一步最有价值的是：

1. 真实补完一批人工结论
2. 再看这块覆盖状态是否从“缺很多”变成“只缺少数关键字段”
3. 重新生成跨批次汇总
4. 再判断是否正式开启 UI 优化讨论
