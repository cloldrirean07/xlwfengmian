# 2026-06-27_跨批次摩擦点汇总接入记录

## 1. 本轮目标

- 在单批次结构化摩擦点模板之后，再补跨批次汇总能力。
- 让 UI 讨论不只看某一批的观察，而是看重复出现的问题。

## 2. 本轮完成内容

已完成：

- 新增跨批次摩擦点汇总 report / markdown / obsidian record
- 新增 preview / export 应用层
- 新增服务端接口：
  - `POST /api/batch-run-friction-summary-preview`
  - `POST /api/batch-run-friction-summary-export`
- 新增前端面板：
  - `跨批次摩擦点汇总`
- 新增自动化测试覆盖

## 3. 本轮判断逻辑

当前判断分三档：

- `strong-signal`
- `emerging-signal`
- `insufficient-signal`

其中：

- 3 批且至少 2 类重复摩擦点 -> `strong-signal`
- 2 批且至少 1 类重复摩擦点 -> `emerging-signal`
- 其他情况 -> `insufficient-signal`

## 4. 本轮验证

应验证内容：

- `node --check`
- `npm test`
- 页面中新的跨批次汇总面板可预览
- 可导出到 Obsidian

## 5. 当前推进判断

这层能力补完后，项目已经不是只会记录单批次问题，而是开始能回答：

- 哪些摩擦点已经重复出现
- 哪些更像值得优先改的产品问题
- 哪些已经足够稳定到可以进入 UI 讨论

## 6. 当前对 UI 时机的影响

当前更合理的判断方式变成：

1. 先看 UI readiness gate 是否达标
2. 再看跨批次摩擦点汇总里，重复问题是否已经足够稳定

只有这两层都更稳时，正式讨论 UI 才更有价值。

## 7. 下一步建议

- 继续补真实批次试跑，不着急直接做视觉方案。
- 等跨批次汇总里出现更稳定的重复类别后，再单独开 UI 优化讨论。
