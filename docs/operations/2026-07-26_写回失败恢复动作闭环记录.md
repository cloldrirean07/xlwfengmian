# 写回失败恢复动作闭环记录

## 1. 本轮目标

[事实] 继续按 PI Engine 维护模式推进写回态错误状态闭环。

[事实] 本轮目标是让写回操作失败后，在动作状态卡片内直接提供可恢复入口，避免用户只看到“需复查”而不知道下一步操作。

## 2. 实现映射

[事实] Requirement Spec 对应实现范围：

- 页面范围：写回态中的“正式写回门禁总览”。
- 组件范围：写回操作执行状态卡片。
- 操作范围：仅复用既有 `data-review-followup-action` 动作，不新增接口、不新增写回动作。
- 失败恢复：
  - 安全预览导出失败：显示“重新导出安全预览”。
  - 写回状态检查失败：显示“重新检查写回状态”。
  - 正式写回失败：显示“重新检查写回状态”，先回到门禁检查，避免直接诱导重复写回。
- 边界：不改变正式写回门禁规则，不绕过人工确认，不改变 readiness 接口契约。

## 3. 实现范围

[事实] `public/app/renderers.js` 已新增 `getWritebackActionRecovery`：

- 为失败状态映射恢复入口。
- 恢复入口统一渲染为 `data-review-followup-action` 按钮。
- 正式写回失败复用状态检查动作，不直接复用正式写回动作。

[事实] `public/styles.css` 已新增 `.writeback-action-recovery`：

- 按钮占满动作卡片宽度。
- 保持最小点击高度，避免与状态说明挤压。

## 4. 测试覆盖

[事实] `tests/coverAssistantService.test.js` 已补充断言：

- 写回动作样式体系包含 `.writeback-action-recovery`。
- readiness 缺失但状态检查失败时，空态仍展示恢复入口。
- 正式写回失败时，动作状态区展示“重新检查写回状态”。
