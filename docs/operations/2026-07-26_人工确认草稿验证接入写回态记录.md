# 人工确认草稿验证接入写回态记录

## 1. 执行背景

[事实] 本轮继续按“AI项目资料”的 PI Engine 维护模式推进真实案例数据闭环。

[事实] 上一轮已经证明：

- 建议填写块会打开正式写回门禁。
- 保守填写块会保持门禁锁定。

[事实] 但验证结果只存在于命令行输出和 `outputs` 报告中，尚未进入写回态总览。

## 2. 本轮目标

[事实] 将人工确认草稿门禁验证结果接入写回态总览，让刷新门禁状态时同步展示草稿验证结果。

[事实] 本轮只读项目内草稿，不写入 Obsidian 安全预览，不修改真实批次试跑记录，不执行正式写回。

## 3. 实现映射

| Requirement Spec / PRD 规则 | 本轮处理 |
| --- | --- |
| 正式写回前必须有确认状态 | 写回态总览新增人工确认草稿验证状态 |
| 未确认时不执行正式写回 | 新增接口只读草稿验证结果，不触发写回 |
| 用户需要看到下一步门禁状态 | 刷新门禁状态时同步读取 readiness 与草稿验证 |
| 保持历史功能可用 | 沿用现有 `renderWritebackGateOverviewStatus` 与刷新按钮 |

## 4. 本轮改动

[事实] 新增 application：

`apps/web/src/application/runManualConfirmationDraftValidationPreview.js`

[事实] 新增服务端接口：

```text
GET /api/batch-review-manual-confirmation-draft-validation
```

[事实] 新增前端 API：

`previewBatchReviewManualConfirmationDraftValidation`

[事实] 写回态状态新增：

`latestManualConfirmationDraftValidation`

[事实] 写回态总览新增“人工确认草稿验证”只读面板，展示：

- 草稿验证是否通过。
- 建议填写块是否会打开门禁。
- 保守填写块是否会保持锁定。
- 人工结论、仍需手改和写回许可的解析结果。

## 5. 验证结果

[事实] `npm test -- --test-reporter=dot` 已通过。

[事实] `npm run build` 已通过。

[事实] `npm run validate:manual-confirmation-draft` 已通过。

[事实] `GET /api/health` 在 `http://127.0.0.1:3199/` 返回正常。

[事实] `GET /api/batch-review-manual-confirmation-draft-validation` 返回 `ok=true`，并确认：

- 建议填写块：`canProceedToFormalWrite=true`
- 保守填写块：`canProceedToFormalWrite=false`

[事实] `GET /api/batch-review-manual-formal-write-readiness` 仍返回 `awaiting-safe-write-confirmation`，说明本轮没有擅自写入正式安全预览，也没有打开正式写回门禁。
