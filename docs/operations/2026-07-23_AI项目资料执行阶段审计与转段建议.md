# AI项目资料执行阶段审计与转段建议

- Skill：`ai-pi-engine`
- 模式：维护模式
- Requirement Spec：`docs/prd/AI封面创意助手重做_Requirement_Spec_v0.1.md`
- PRD：`docs/prd/AI封面创意助手_MVP重做_主路径与工作台重做.md`
- 架构计划：`docs/architecture/AI封面创意助手产品线重做架构计划_v0.1.md`

## 2. 当前阶段判断

当前项目已经完成多轮 PI Engine 维护模式闭环。近期闭环集中在：

- 输入准备失败保留
- 素材上传失败保留
- 首轮和二轮失败后回到可操作区
- 工作区建议失败和反馈保存失败承接
- 真实案例、平台案例、批次复盘、正式写回等失败后保留重试入口

这些改动让系统异常状态更稳，但它们属于“维护补强”，不是“产品线结构重做”的主体。

## 3. 为什么会出现重复感

重复感来自执行模式，而不是来自 PRD 本身。

过去几轮实际形成了固定循环：

```text
读取 AI 项目资料 -> 查 PRD -> 找一个异常承接缺口 -> 改一小段代码 -> 补测试 -> 写闭环记录
```

这个循环在早期是必要的，因为主链路中确实有不少失败状态缺口。但现在继续沿用同一循环，边际收益开始下降：

- 每轮都能找到一个小异常承接点
- 每轮都能让测试数量增加
- 但每轮都没有真正改变首页仍像“总控制台”的结构问题

因此，继续补零散异常会让项目看起来在动，但不会明显靠近“产品线重做”的核心目标。

## 5. 当前仍未真正解决的问题

### 5.1 首页仍是混合控制台

当前 `apps/web/public/index.html` 同时承载：

- 用户主链路
- 主链路辅助验证工具
- 真实案例维护链
- 验证与复盘工作台

这与 PRD 目标“把产品重新收束为一条清晰主路径”仍有差距。

### 5.2 已有能力的产品优先级没有彻底重排

已有文档 `docs/architecture/首页页面分层与拆页建议_v0.1.md` 已指出：首页长期应保留用户主链路，辅助工具、案例维护、复盘驾驶舱需要降低同屏权重或拆分。

当前代码已经有 `workspace-group-tools`、`workspace-group-cases`、`workspace-group-validation` 三组过渡结构，但仍然留在同一个首页中。

### 5.3 下一步不该继续以异常承接为主

近期异常承接已经覆盖很多关键点。继续补小缺口会变成“形式上符合 PI Engine，实质上绕开产品线重做”。

## 6. 建议转段

建议从下一轮开始停止默认寻找零散异常承接，改为进入“产品线结构重做确认”。

优先级建议：

1. 先确认首页是否进入拆页或准拆页阶段。
2. 再确认主链路首屏和工作区是否作为前台产品体验保留。
3. 最后处理案例维护链和复盘驾驶舱的入口降级或独立化。

## 7. 下一阶段推荐方案

### 方案 A：不拆路由，只做首页主次重排

适合目标：

- 快速让首页更像真实产品
- 不引入路由和文件结构变化
- 保留当前所有测试和入口

核心动作：

- 首页第一屏只保留输入准备、首轮、工作区、二轮入口
- 工具、案例、复盘继续折叠
- 首页导航改成主路径优先

风险：

- 页面仍然偏长
- 内部工作台仍在首页，只是被降低权重

### 方案 B：准拆页，保留单页但建立三类页面视图

适合目标：

- 不引入真正路由
- 但用户感知上分成“创作主线 / 案例维护 / 复盘驾驶舱”

核心动作：

- 增加顶部视图切换
- 每次只显示一个主区域
- 当前锚点和功能不删，只改变可见层级

风险：

- 需要重新检查所有锚点和跳转
- 测试需要覆盖视图切换

### 方案 C：正式拆页

适合目标：

- 明确进入产品线重做
- 首页成为真正用户主链路
- 案例维护和复盘驾驶舱独立成内部工作台

核心动作：

- 首页保留主链路
- 案例维护迁到独立页面或视图
- 复盘驾驶舱迁到独立页面或视图

风险：

- 改动面最大
- 需要先确认是否允许新增路由或页面文件

## 8. 推荐结论

当前最合理的下一步是：

**先执行方案 B：准拆页，保留单页，建立三类页面视图。**

原因：

- 符合 PRD 的主路径收束目标
- 不立即引入正式路由风险
- 能明显降低“继续小补丁”的重复感
- 能为后续正式拆页保留结构余地
