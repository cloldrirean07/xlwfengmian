# 人工确认草稿门禁验证闭环记录

## 1. 执行背景

[事实] 本轮继续按“AI项目资料”的 PI Engine 维护模式推进真实案例数据闭环。

[事实] 上一轮已经生成 `manual-confirmation-draft.md`，但尚未证明“建议填写块”和“保守填写块”分别会造成什么门禁结果。

[事实] 本轮目标是把人工确认草稿变成可验证对象：在不写入 Obsidian 安全预览、不执行正式写回的前提下，验证两个填写块的 readiness 影响。

## 2. 实现映射

| Requirement Spec / PRD 规则 | 本轮处理 |
| --- | --- |
| 正式写回前必须有写回预览和确认状态 | 新增草稿验证脚本，只验证确认块，不执行写回 |
| 未确认写回时不修改目标记录 | 只读取项目内 `manual-confirmation-draft.md`，不改 Obsidian 文件 |
| 人工复盘结论为正式写回前必填 | 复用 `parseBatchReviewManualSafeWritePreviewNote` 的人工结论校验 |
| `仍需手改` 非空时不得进入正式写回 | 保守填写块验证结果保持 `canProceedToFormalWrite=false` |
| 明确许可后才允许进入正式写回 | 建议填写块验证结果为 `canProceedToFormalWrite=true` |
